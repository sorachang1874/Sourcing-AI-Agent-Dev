# Pre-Agent Contract Review

> Status: Active W10 review tracker. Use with `DURABLE_EXECUTION_RUNTIME_CONTRACT.md`, `AGENT_OPERATION_CONTRACT.md`, `CANONICAL_SERVING_PROJECTION_CONTRACT.md`, `CRM_STATE_CONTRACT.md`, and `PERSON_ASSET_EVIDENCE_ASSERTION_CONTRACT.md` before Phase 13 Agent UI/graph work.

## Purpose

Phase 13 Agent interaction can only call durable owners safely if each module has a single normal owner, fail-closed readers, explicit command/action surfaces, and fast preflight coverage. This review is the W10 evidence ledger: it records what is already safe for Agent/Operation use, what remains migration-only, and what still needs a direction decision.

## Review Rules

- A module is Agent-callable only through `AgentAction`, `OperationRun`, `workflow_commands`, or an explicit read-only API.
- New durable runtime, OperationRun, workflow-current-state, CRM task/current-state, and Agent-callable execution state must be PG-only. Do not add SQLite DDL/fallback for these tables.
- Public readers must not repair state, synthesize fallback rows, or write module state during reads.
- Fast preflight must include public-reader source checks for projection/person/company/media read methods. Normal read methods must not call `backfill`, `rebuild`, `upsert`, `update`, `write`, `repair`, or command-planning helpers; repair must stay in explicit operator/Operation command owners.
- Migration bridges must be report-visible, signoff-gated, and paired with a deletion condition.
- Retired Public Web aliases must not receive normal priority-lane handling. `/api/target-candidates/public-web...` may remain only as unconditional `410` compatibility branches; interactive/light-lane treatment is reserved for canonical `/api/crm/records/public-web...` routes. Normal frontend source and frontend contract/adapter files must not contain `/api/target-candidates/public-web` at all; `TargetCandidatePublicWeb*` type names are temporary naming debt only and cannot own endpoint routing.
- Historical candidate-document fallback is migration/reuse compatibility only. `SOURCING_ENABLE_LEGACY_CANDIDATE_DOCUMENTS_FALLBACK` must default off; normal projection/public-reader paths must pass `allow_candidate_documents_fallback=False` and fail closed when canonical materialized artifacts are not ready.
- Expensive W6/nightly runs are not contract discovery tools. Field owner drift, hidden fallback, or missing owner evidence must fail in fast preflight first.
- Normal owner-registry workflow commands must have non-legacy `activity_spine_policy` coverage from `durable_runtime.workflow_command_activity_spine_policy`. `legacy_internal_pending_activity_spine` is now a fail-closed policy state only; adding one back to the normal owner registry or exposing it through the action registry is a W10 preflight failure.
- Significant implementation or contract slices require the independent review gate in `docs/INDEPENDENT_REVIEW_GATE.md` after targeted/fast preflight and before W6/nightly, live provider validation, founder/manual signoff, or Phase 13 work. The reviewer must not be the author and must store a GO/NO-GO review artifact.

## Confirmed Architecture Decisions

### W11d Operation-Native Discovery

Direction confirmed: `acquisition.scale.plan` must not turn `acquisition_discovery_lanes` into a mini workflow engine. W11d introduces a generic activity spine and a domain read model:

- PG-only `workflow_activity_runs` is the bounded side-effect boundary for provider submit/poll/fetch, parsing, export chunking, and other long-running owner work.
- PG-only `workflow_activity_attempts` records individual execution attempts, provider refs, retry/rate-limit state, errors, input/output envelopes, and artifact refs.
- PG-only `workflow_entity_deltas` records explainable entity-level effects from activities, including no-op / not-applied reasons before a candidate, evidence, asset, assertion, or projection membership is produced.
- PG-only `acquisition_discovery_lanes` is acquisition-specific current-state/read-model materialization. It references `source_command_id`, `activity_run_id`, `provider_ref`, `artifact_refs`, `entity_counts`, and `downstream_command_ids`; it does not own provider execution state.
- `acquisition.scale.plan` may materialize planned lanes/activity rows, but executable `linkedin.discovery_query.run` commands must be consumed by the operation-native discovery owner from `acquisition_run_id` / `lane_id` / `activity_run_id`, without legacy job shell, `job_id`, and snapshot shell requirements.
- Provider-backed discovery execution writes candidate/evidence deltas through `workflow_entity_deltas` before projection/profile-refill commands consume them.

The long-term Agent-facing contract is Operation/Command/Activity, not lane/table mutation. Agent may query lanes for explanation through read-only `/api/workflow/discovery-lanes`, but retry/cancel/resume/debug controls target typed command/activity APIs.

Current implementation status: first slice adds PG-only activity/lane/entity-delta storage and makes `acquisition.scale.plan` materialize `workflow_activity_runs` and `acquisition_discovery_lanes` with `planned_pending_owner`. A running `acquisition.scale.plan` can be cancelled only before a discovery command exists and before any activity attempt starts; the owner-specific cancel marks the linked acquisition run, activity run, and discovery lane `cancelled_before_discovery`. `continue_acquisition_run -> linkedin.discovery_query.run` now requires `acquisition_run_id`, `lane_id`, and `activity_run_id`; legacy `job_id`/`snapshot_id` discovery payloads are rejected as normal Agent input. The `operation_native_discovery_activity_owner` recovery phase claims these commands, records `workflow_activity_attempts`, calls the provider-backed discovery primitive with `runtime_mode=operation_native_discovery`, writes model-safe activity artifacts, records positive candidate `workflow_entity_deltas`, updates the acquisition lane/read model, and plans downstream `linkedin.profile_fetch.activity.run` commands for W11e. Retryable provider failures remain retry-wait activity attempts. The legacy search-seed queue owner skips operation-native commands report-visibly and does not claim them; the legacy job shell discovery owner is not invoked by this boundary. Activity, attempt, entity-delta, and discovery-lane query rows now expose `control_target` back to the owning `workflow_command` plus its `display_contract`, `control_policy`, `control_state`, `activity_spine_policy`, and `fallback_status=fail_closed`, so Agent/debug callers never need to infer titles, categories, retry/cancel/resume behavior, or Activity-spine requirements from lane or evidence rows.

### W11e Operation-Native Profile Fetch Activity

Direction confirmed: Agent-facing profile fetch must use the generic Activity spine, not the legacy job-scoped profile refill shell. `fetch_profile_sample` defaults to `linkedin.profile_fetch.activity.run`, and `continue_acquisition_run` may plan the same command from discovery entity deltas. The command owner is `linkedin_profile_activity_owner`.

- `linkedin.profile_fetch.activity.run` consumes profile URLs or candidate `workflow_entity_deltas`.
- The owner records a `workflow_activity_run`, a local cache/planning `workflow_activity_attempt`, and profile `workflow_entity_deltas`.
- Registry cache hits become `profile_cache_hit` deltas; unfetched profiles become `profile_fetch_required` deltas with `provider_owner_required=true`.
- The command does not create a legacy job shell, does not call `queue_workflow`, and does not invoke `linkedin.profile_refill.submit_batch` as an Agent normal path.
- Claimed/running `linkedin.profile_fetch.activity.run` commands support owner-specific cancel only before cache lookup starts, before any profile EntityDelta is recorded, before downstream commands are planned, and after lease expiry or explicit force. The owner marks the linked activity/run state `cancelled_before_cache_lookup`; after cache lookup or downstream planning begins, cancellation fails closed and recovery must resume/retry through Command/Activity APIs.
- W11f adds `linkedin.profile_fetch.provider.fetch`, which consumes `profile_fetch_required` deltas, records provider `workflow_activity_attempts`, writes fetched raw-path evidence into `linkedin_profile_registry`, and emits `profile_provider_fetched` deltas.
- W11f follow-up adds `linkedin.profile_terminal.admit`, which consumes `profile_cache_hit` / `profile_provider_fetched` deltas and emits `profile_terminal_recorded` deltas. It deliberately does not mutate projection membership; the projection-admission owner must consume terminal deltas in a later W11 slice.
- W11g adds `projection.profile_admission.apply`, which consumes `profile_terminal_recorded` deltas, writes canonical run-scope `serving_projection_members` through `serving_projection_owner`, and emits `projection_member_admitted` deltas. It is the only normal Agent-callable path from operation-native profile terminal facts into projection membership.
- W11h keeps current run visibility separate from background asset upkeep: after operation-native projection admission, existing `projection.person_search_index.build` and `collection.authoritative.merge` commands are planned on the same Operation workflow id without a legacy job shell or normal-path `job_materialization_items` write. Their command owners record ActivityRun/Attempt/EntityDelta evidence for index pages and collection pointer effects, so Agent/debug queries do not need to infer those effects from command result JSON.
- W11h follow-up applies the same evidence rule to profile URL terminal recording, local apply, board-visible publication, legacy job result-view projection publication, and facet/layering builds: `linkedin.profile_url_terminal.record` records per-profile-url `profile_url_terminal_record` EntityDeltas before local apply can treat registry terminal state as proven; `linkedin.local_profile_delta.apply` records `local_profile_delta` EntityDeltas for completed, partial, waiting-prerequisite, retry-wait, failed, and already-completed effects; `projection.board_visible_patch.publish` records `board_visible_patch` EntityDeltas for completed, waiting-prerequisite, retry-wait, and failed board publication effects; `projection.run_scope.finalize` records `run_scope_projection` EntityDeltas for published, obsolete, retry-wait, and failed finalization effects; `projection.facet_layering.build` records `facet_layering` EntityDeltas for completed, partial, retry-wait, and failed layering effects. These commands are not automatically Agent-callable; exposure still requires the action registry allowlist.
- W7f follow-up brings CRM Public Web run phases onto the same Activity spine: each per-run phase command records one ActivityRun, one ActivityAttempt, and a run-level `crm_public_web_run` EntityDelta keyed by CRM Public Web run id. `crm.public_web.documents.fetch` additionally records document-level `public_web_document` EntityDeltas from `document_fetch_payload.json`, and `crm.public_web.signals.materialize` records signal-level `public_web_signal` EntityDeltas from the materialized `person_public_web_signals` read model plus canonical `person_asset` / `person_evidence` EntityDeltas for the PersonAsset layer under the same activity id. These deltas do not create a separate Public Web state machine.
- W7d/W11 follow-up brings export owners onto the same Activity spine: projection export and CRM Public Web export commands record ActivityRun/Attempt evidence and an export EntityDelta with artifact refs. Export rows/artifacts remain read models/output artifacts, not execution truth.
- W7c/W11 follow-up brings Excel intake onto the same Activity spine: `excel.intake.run` records an ActivityRun/Attempt when it starts the async local owner and records an `excel_intake_job` EntityDelta when the thread reaches a terminal status. Claimed/running Excel intake commands now support cooperative owner-specific cancel through `excel_intake_owner.cancel_excel_intake_run_command`; cancellation records a durable command marker, cancelled Activity/Attempt/EntityDelta evidence, and thread/materialization checkpoints before terminalization. Claimed/running resume goes through `excel_intake_owner.resume_excel_intake_run_command`, records control evidence, and requeues without starting a local thread or writing intake materializations from the request path.
- W9/W11 follow-up brings CRM writer commands onto the same Activity spine: `crm.record.add_from_projection`, `crm.record.update`, `crm.note.add`, and `crm.task.create` record ActivityRun/Attempt evidence and EntityDeltas for the CRM record plus event/note/task effects. CRM tables remain the CRM read model and audit state; they are not the execution owner. Running CRM writer commands expose owner-specific cancel before mutation attempt through `crm_writer.cancel_before_mutation_attempt` and owner-specific resume through `crm_writer.resume_crm_writer_command`; cancel is allowed only before ActivityAttempt/EntityDelta/downstream command creation and after lease expiry or explicit force, while resume may only record control evidence and requeue the command. CRM mutation remains owned by the next `crm_writer` command claim.
- W11 company Public Web refresh now uses the same Activity spine with a split root/phase boundary: `refresh_company_public_web_assets` actions plan `company.public_web.refresh`; the root command only plans `company.public_web.source.collect`; source collection writes or joins source-specific company Public Web rows/artifacts with canonical asset sync deferred; it then plans `company.public_web.assets.materialize`, which syncs model-safe facts into `CompanyAsset` / `CompanyEvidence` and records `company_public_web_run`, `company_asset`, and `company_evidence` EntityDeltas. The source-collection join branch must not opportunistically sync canonical company facts. The synchronous company Public Web refresh service remains a manual API/CLI service entry, not the Agent normal path.

### Future Activity-Spine Extension Rule

Any new Agent-callable bounded side effect must first add or reuse a typed `workflow_commands` boundary, explicit `workflow_command_control_policy`, explicit `workflow_command_activity_spine_policy`, `workflow_activity_runs`, `workflow_activity_attempts`, and `workflow_entity_deltas` evidence. Domain tables may be added only as efficient read models for product queries, and they must reference the command/activity causality instead of owning retry, cancel, resume, provider attempts, or recovery state.

Agent, UI, or recovery code must never directly mutate lane, registry, projection, CRM, Public Web, Excel, export, evidence, or asset rows to simulate execution progress. They must call Operation/Command APIs or owner-specific command handlers, then read Activity/Attempt/EntityDelta/domain read-model rows for explanation.

Provider after-start control is an extension of durable Activity/Attempt semantics, not a replacement for item-level business retry contracts. LinkedIn profile fetch keeps the old scheduler invariant: normal-wave successful URLs continue through terminal/profile admission immediately, while only failed or unresolved URLs enter a retry bucket. Operation-native `linkedin.profile_fetch.provider.fetch` must therefore emit `profile_provider_fetched` for successful URLs, emit `profile_provider_retry_bucketed` for failed URLs, and plan a retry-wave provider command with `provider_attempt_scope='retry_wave'`, `retry_wave_index`, `retry_unit='linkedin_url_key'`, and `retry_strategy='bucketed_entity_retry_after_normal_wave'`. It must not mark the whole provider command `retry_wait` merely because one URL failed, must not retry successful URLs with failed URLs, and must not mix retry-wave URLs back into unfinished normal-wave work. After the retry budget is exhausted, failed URLs emit `profile_provider_retry_exhausted`; late/old provider results remain quarantined evidence until a future explicit owner command adopts them.

The same rule applies to DataForSEO Standard Queue batch transport. A batch `task_post` can carry many query tasks, but every query has a caller-assigned stable `task_key` analogous to the LinkedIn URL key. That key must be sent as the provider task tag, returned as `query_identity_key`, and used by downstream joins/retries/manifests/outcomes; array order and candidate display ordinal are display compatibility only. Public Web query task keys must be scoped to stable candidate/query identity, not the candidate's position in the current batch. Search seed discovery worker keys must likewise be scoped to stable search query signature, bundle, and employment scope, not the query's ordinal in the current query list. Exploratory enrichment query keys must be scoped to stable candidate/query identity, not `candidate_id::index`. Provider/search-chain code must fail closed when a batch spec lacks `task_key`; it must not generate identity from query text, task id, candidate ordinal, or array position. Provider response mapping is allowed only through provider-echoed `tag` or unambiguous provider-echoed `keyword`. Missing provider identity is an item-level retry/failure, not permission to bind by request order. Failures are query-item outcomes: successful task ids remain submitted, only failed query tasks can be retried, and the retry metadata must expose `retry_unit='search_query'` plus `retry_strategy='dataforseo_batch_failed_query_retry_only'`. A batch `task_get` can fetch many ready task ids concurrently, but one failed `task_get` must not discard sibling successes; failed fetch evidence is scoped to `retry_unit='dataforseo_task_id'` with `retry_strategy='dataforseo_task_get_failed_task_retry_only'`. DataForSEO readiness probes must report provider-pending status codes `40601` and `40602` as waiting metadata, not terminal failure; after a bounded poll budget, an owner may reset only the affected query task with the same `task_key`, preserve `previous_task_ids`, and report `provider_task_reset_reason`, but must not resubmit sibling queries or the enclosing batch. Provider-pending long-tail waiting has its own `max_provider_pending_wait_seconds` hard budget. `max_remote_search_wait_seconds` may terminalize unknown never-ready tasks, but it must not terminalize explicit `40601` / `40602` tasks before the provider-pending budget; those tasks stay `waiting_remote_search` with `provider_pending_wait_deferred` visible in metrics/checkpoint. Public Web, seed-discovery, and exploratory-enrichment readers must consume these as item-level checkpoints rather than falling back to whole-batch retry or whole-batch failure.

Generic command resume is limited to `retry_wait`, where it clears `not_before_at` and lets the owner re-claim the command. `claimed/running` resume is fail-closed unless the command owner registers explicit owner-specific resume support. Implemented cases: CRM Public Web phase commands may be requeued through `crm_public_web_owner.resume_crm_public_web_phase_command` only when `payload.run_id` exists and the command lease is expired or the caller uses explicit force; projection and CRM Public Web export commands may be requeued through their export owners only when the artifact has not been published and the command lease is expired or forced; orchestration, provider-attempt, and domain-mutation commands may be requeued only through their registered owner-specific delegates. Each owner records Activity/Attempt/EntityDelta resume evidence and moves the command back to queued without mutating domain read models directly. Domain-mutation cancel uses `workflow_domain_owner.cancel_before_domain_mutation_attempt` only before ActivityAttempt/EntityDelta/downstream evidence; domain-mutation resume uses `workflow_domain_owner.resume_domain_mutation_command`. Neither delegate may write registry, projection, collection, snapshot, CRM, Public Web, media, or asset tables from the control API. Unsupported running commands expose `running_command_requires_owner_specific_resume` in `control_state.disabled_reasons.resume`, a category-specific `running_resume_blocked_reason`, and `running_resume_upgrade_requirements`; the placeholder `owner_specific_resume_not_implemented` is blocked for normal owner-registry commands. `workflow_service_metrics.durable_command_owner_contracts` owns `control_policy_violation_count` and includes control-policy drift in `violation_detected`; scripted signoff with `require_durable_command_owner_contracts=true` must also block active command contracts whose `control_policy` is missing, not `fail_closed`, or still uses placeholder running cancel/resume policy fields, even when owner and causality counts are clean. Agent/UI code must not use resume as a generic repair button for in-flight provider calls, artifact writes, local threads, or domain mutations.
- Status-specific command controls must also be explicit. `durable_runtime.workflow_command_control_state` combines current command status with the policy and is the only source for allowed `cancel` / `retry` / `resume` actions, cancel mode, disabled reasons, and module-state mutation expectation. Command records, command control responses, and Activity/Attempt/EntityDelta/Lane `control_target` records must expose this `control_state`, so Agent/UI callers do not infer buttons from status strings.
- Status-specific OperationRun controls must also be explicit. `operation_runtime.operation_run_control_state` is the source of truth for dispatch/resume/retry/cancel availability on OperationRun rows and control responses. Operation Queue UI must render run-level controls from top-level/row `control_state.allowed_actions` and `disabled_reasons`, not from local terminal-status sets or status-string heuristics. If an operation retry creates a child OperationRun, the UI must select the returned child run instead of continuing to render controls for the terminal parent.
- Workflow command display must be registry-owned. `durable_runtime.workflow_command_display_contract` is the source of truth for command display labels, product category, and command description. `/api/workflow/command-registry`, `/api/workflow/commands`, `/api/workflow/commands/{command_id}`, workflow command control responses, and Activity/Attempt/EntityDelta/Lane `control_target` records must expose this `display_contract`; frontend and Agent UI may show `command_type` as a debug id but must not derive product copy or grouping from command type strings.
- Operation UI display copy must fail closed. If `operation_action.display_contract`, `operation_run.display_contract`, or `workflow_command.display_contract` is absent, `/operations` must render an explicit missing-contract label/category and surface that as a frontend-contract regression; it must not fallback to `owner_module`, `owner`, `operation_type`, `action_type`, or `command_type` for product titles/categories.
- Activity-spine evidence must be policy-owned. `durable_runtime.workflow_command_activity_spine_policy` is the source of truth for whether a command must write ActivityRun/Attempt/EntityDelta evidence, only plans a downstream activity boundary, or is orchestration-only. The normal owner registry currently has no `legacy_internal_pending_activity_spine` command types; the operation action registry still fail-closes any such command if a future migration accidentally reintroduces one.
- Durable owner signoff treats display and Activity-spine policy as first-class contracts. `workflow_service_metrics.durable_command_owner_contracts` owns `display_contract_violation_count` and `activity_spine_policy_violation_count`; both are included in `violation_detected`, and scripted signoff blocks active command contracts that omit display copy, lose fail-closed ownership, or regress Activity-spine policy to `legacy_internal_pending_activity_spine`.
- Operation queue summaries must be operation/runtime-owned. `operation_run.status_summary` may only summarize `operation_runs`, `operation_events`, and `workflow_commands`, with command drill-down delegated to `workflow_command.execution_summary`; it must not read CRM/Public Web/projection/Excel/export/registry/lane read models to make an operation look complete, failed, or cancellable.
- Command status/provenance summaries must be Activity-spine-owned. `workflow_command.execution_summary` on command detail, and optional list summaries through `include_execution_summary=true`, may only read `workflow_activity_runs`, `workflow_activity_attempts`, and `workflow_entity_deltas`; it must expose `fallback_status=fail_closed`, `fallback_used=false`, and `module_state_mutated=false`. It must not stitch progress from CRM/Public Web/projection/Excel/export/registry/lane read models, because those are domain materializations rather than execution truth.
- Agent command exposure must be ActionRegistry-owned. `activity_spine_policy.agent_callable` means a command has the technical Activity/Attempt/EntityDelta spine required for future Agent orchestration; it is necessary but not sufficient for product exposure. The ActionRegistry allowlist (`operation_runtime.ActionRegistry.allowed_workflow_command_types`) is the only normal Agent exposure gate. Public operation registries must expose `workflow_command_exposure_gate=operation_runtime.ActionRegistry.allowed_workflow_command_types`, `workflow_command_exposure_status`, and per-command `agent_exposure_gate` / `agent_exposure_status` so UI/Agent code never infers callable commands from the durable owner registry alone.
- Action-level command control summaries must also be ActionRegistry-owned. `workflow_command_control_summary` is derived from `allowed_workflow_command_contracts` and exposes maturity/gap/category counts plus UI guidance for closed or partially closed command-control surfaces. Agent/UI code may use it to explain that an action can plan a command but may not be safely interruptible while running; it must not recompute those summaries from command type strings or owner names.
- Workflow command exposure must be explicit on both registry and concrete command rows. `/api/workflow/command-registry` is a durable owner/control registry, not an Agent action allowlist. Every command-registry entry and every `/api/workflow/commands` list/detail row must expose the same `agent_exposure_gate` and `agent_exposure_status`; commands that are technically runnable but not ActionRegistry-allowlisted must say `not_action_registry_allowlisted`, so Agent/UI callers cannot treat owner-registry membership or a visible command row as product permission.
- Operation UI command status copy must be Activity-spine-owned. The `/operations` page may show command counts, latest effect, reason, entity, and sample truncation only from `workflow_command.execution_summary`; it must not infer command effects from command type names, timestamps, domain read models, or owner-private result JSON.
- Operation UI Activity drill-down is read-only runtime inspection. `/operations` may query `/api/workflow/activities`, `/api/workflow/activity-attempts`, and `/api/workflow/entity-deltas` by command id, but all dispatch/resume/retry/cancel controls must still go through OperationRun or WorkflowCommand control APIs.
- Activity/Attempt/EntityDelta/Lane rows are read-only evidence, not mutable workflow state. Each row returned from `/api/workflow/activities`, `/api/workflow/activity-attempts`, `/api/workflow/entity-deltas`, and `/api/workflow/discovery-lanes` must expose `module_state_mutated=false`, a `mutation_contract` beginning with `read_only_`, and a `control_target` pointing to the owning workflow command when command causality exists. That `control_target` must include command-owned `display_contract`, `control_policy`, `control_state`, `activity_spine_policy`, and `fallback_status=fail_closed`. Agent/UI callers must never mutate or control Activity/Attempt/Delta/Lane rows directly, and must not derive display copy or control behavior from their domain fields.
- Operation UI command control is WorkflowCommand-owned. `/operations` may render command-level cancel/resume/retry buttons only from `workflow_command.control_state.allowed_actions` / `disabled_reasons`, and those buttons must call `/api/workflow/commands/{command_id}/cancel|resume|retry`; no command status string, owner name, Activity row, or domain read model may infer control capability.
- Operation UI command control must surface rejected controls. If the WorkflowCommand control API returns `invalid`, `not_found`, or another non-success status, the frontend must show the backend `reason` / `command_status` rather than treating a refresh as success.
- Command control responses must expose `display_contract`, `control_policy`, and `activity_spine_policy` at the top level as well as on `workflow_command`, so Agent/UI callers do not need to inspect nested command detail or infer labels, control behavior, or Activity-spine requirements from command type strings.
