# Workflow Progress Contract

> Status: Current contract. Read with `FRONTEND_API_CONTRACT.md`, `EVENT_LEVEL_WORKFLOW_RESPONSE.md`, and `TESTING_PLAYBOOK.md` when changing provider-backed workflow progress, result-view lifecycle, candidate board streaming, or browser/scripted observations.

This document defines where progress numbers come from and how the frontend may display them. The goal is to avoid mixing provider discovery, profile fetch, local materialization, and frontend pagination into one ambiguous counter.

## Source Of Truth

`GET /api/jobs/{job_id}/progress`, `GET /api/jobs/{job_id}/dashboard`, and `GET /api/jobs/{job_id}/candidates` must expose the same canonical progress contracts:

- `linkedin_stage_1_progress`: Stage 1 acquisition and LinkedIn profile-fetch progress.
- `board_runtime_state`: candidate-board publication, business sync, facet readiness, and filter scope.
- `result_view_lifecycle`: which snapshot/result view is being served and how much of the delta is visible on the board.
- `execution_phase_contract`: user-facing phase label/detail and whether Public Web Stage 2 is actually applicable.

`GET /api/jobs/{job_id}/board-patches` is the light progress-transport endpoint for candidate-board row publication. It must return ordered durable `job_board_visible_patches`, the same `board_runtime_state` and `result_view_lifecycle`, and card-quality counters without returning candidate rows.

The frontend must not infer these states from timeline prose, worker counts, local candidate array length, or cached pagination length.
If a workflow reuses the `public_web_stage_2` timeline slot for local company-asset archival, `execution_phase_contract.public_web_stage_applicable` must be `false` and `stage_title_overrides.public_web_stage_2` must carry the local stage title. Excel intake uses this rule to render `公司资产归档`, not `Public Web Stage 2`.

## Contract Preflight Before Nightly/W6

Nightly and W6 signoff are pressure/stability gates. They are not the correct place to discover basic contract ambiguity.

Before running a full PG-backed Nightly/W6 matrix after changing progress, board runtime, projection reader, durable command owner, or frontend result-page contracts:

- Run a fast contract preflight that exercises the changed field owner directly.
- Compare `/progress`, `/dashboard`, `/candidates`, and `/board-patches` for every shared `board_runtime_state` field touched by the change.
- Verify the field owner/source-of-truth table in the relevant contract doc has been updated.
- Verify no public reader uses overlay/job summary/stage-file fallback unless the response reports a migration-only fallback and the scenario explicitly allows it.
- Convert any field-semantic drift found in Nightly/W6 into a fast unit/preflight before rerunning the expensive matrix.

Required field-definition checklist:

| requirement | meaning |
| --- | --- |
| owner | the writer/reader module allowed to set the field |
| source of truth | table/index/projection/event/current-state payload used to derive it |
| allowed values | complete enum or shape, including unavailable/partial states |
| derivation rule | whether it is original, materialized, or explicitly derived from another field |
| consumers | endpoints, frontend components, smoke/signoff evaluators, exports |
| forbidden sources | fallback ladders or local caches that must not set it |
| migration status | normal path, report-visible bridge, or retired |
| preflight | the fastest test that would fail if semantics drift |

Current explicit distinction:

- `facet_summary_scope` is facet-summary coverage, usually `global_full_population`, `current_served_partial`, `raw_profile_partial`, or `unavailable`.
- `filter_contract.facet_count_scope` is filter-count source/readiness, usually `exact_projection`, `index_partial`, or `unavailable`.
- Frontend and backend must not derive either field from the other. They can only be compared when a preflight asserts the expected relationship for a specific serving mode.

### D-3 approved membership/readiness split

For one canonical membership publication revision:

- `N` is the exact visible `serving_projection_members` population. It owns main candidate sync `N/N`, pagination totals, projection-sourced export totals, and projection-to-CRM source totals.
- `projection.membership_revision` is owned by the serving-projection member-publication UoW and sourced from the existing member semantic-input revision. It is a non-empty opaque equality token that binds summary, page, readiness, export, and CRM input snapshots and invalidates caches when unequal.
- `C` is exact `card_ready_count` (`display_ready_candidate_count` is the board compatibility view). It owns only card-detail progress `C/N`; it does not gate row visibility or redefine `N`.
- `P` is exact `profile_ready_count` from the profile readiness owner. `P` and `C` are independently bounded by `N`; neither must be less than or equal to the other.
- `explicit_profile_capture_candidate_count` comes only from explicit capture-owner evidence. It must not be copied from profile-ready, fetched, card-ready, display-ready, or visible-member counts.
- The public projection reader publishes optional exact capture/needs-completion/low-richness aggregates only when every visible member in that revision carries the corresponding owned `projection_metrics` fact. Mixed legacy membership keeps the affected aggregate unavailable; legacy summaries cannot fill it with either a value or zero.
- A newly authoritative exact publication may correct `N`, `C`, `P`, and other revision-bound aggregates upward, downward, or to zero. Consumers learn which publication is current from the projection/run-link owner, then require token equality; `membership_revision` values are never sorted or compared as versions.
- Exact membership is valid only with `count_scope=exact_projection`, `read_contract.source=serving_projection_members`, `fallback_used=false`, and one consistent revision. Otherwise public progress fails closed as unavailable; it does not show `0/0`, reuse legacy lifecycle/summary counts, or infer a total from loaded rows.
- Missing/token-mismatched direct projection merges fail closed and trigger authoritative re-resolution plus a pinned summary/page re-read. `updated_at`, publication timestamps, patch sequence, and count magnitude are not revision substitutes; `updated_at` cannot distinguish same-timestamp publications.
- A projection summary read pins the member-publication token before aggregating membership/readiness and verifies the same token afterward. A concurrent token change returns not-ready and retries through normal polling; it never emits counts from one revision under another revision's token.
- Public facets remain owned by the revision-fenced `projection_person_search_index`. Initial membership publication exposes facet status as `pending` / `unavailable`; neither the progress adapter nor frontend scans members to publish global facets.
- Projection-bound command planning holds the operation dispatch lock and then the projection publication lock through revision validation and durable planning. Conflicting cancel/publication transactions use pool-safe advisory try-lock acquisition: lock-busy attempts return their PG connection before backoff, and only the successful connection enters the transaction. `POOL_MAX=1` concurrent publication and cancel are a required fast regression. A cancel delayed behind dispatch may retry one committed non-terminal status advance, but a queued command is not thereby cancelled; that cross-table boundary remains R-019.

## Excel Intake Recovery

Excel intake is a workflow with its own durable prepared-input contract:

- `execution_bundle.excel_intake.prepared_contact_batch_path` is the recovery owner for queued Excel groups after upload/schema normalization has succeeded.
- The background thread may receive only the prepared batch path; `_run_excel_intake_workflow` must hydrate from the persisted bundle before invoking `ExcelIntakeService.ingest_contacts`.
- Worker recovery may resume stale `excel_intake` jobs only while they are `queued/running` in `acquiring`, have no `intake_id`, and have a readable prepared batch file. Jobs that already entered ingestion or later stages need a more specific materialization/action repair path, not a blind replay.
- Recovery must not re-parse the workbook or rerun schema inference when a prepared batch exists. The prepared batch, not the original upload request body, is the idempotent replay input.
- User-visible result readiness remains separate from deferred full artifact compaction. Excel boards can serve from the attached snapshot/result view while background artifact rebuild is reported through a distinct materialization/admin channel.
- Excel's local archival stage is not Public Web Stage 2. Dashboard, progress, and history-recovery timeline fallbacks must render it through `execution_phase_contract` or workflow kind as `公司资产归档`.
- Deferred Excel full artifact rebuilds use the canonical `snapshot_full_materialization` durable item kind with an Excel-specific processing branch. The explicit operator/admin entrypoint is `repair-excel-intake-artifacts --job-id ... [--apply] [--run-now]`, and the progress events use `event_family=excel_artifact_materialization`.
- Excel target-candidate import is scoped by the `excel_intake:current_job` marker. It must not walk the full result-view/company asset population, because the board can intentionally contain baseline candidates that were not part of the current workbook.
- Excel workflow completion writes a bounded sidecar `*.excel_intake_row_manifest.json` with matched rows, manual-review rows, unresolved rows, status counts, and truncation metadata. The hot job summary should store only the sidecar reference and counts.
- `GET /api/jobs/{job_id}/progress` must expose Excel row outcomes through `excel_intake_progress`, not timeline text parsing or sidecar reads from the browser. The payload is compact and count-only: total rows, matched rows, target-candidate count, manual-review rows, unresolved/invalid rows, status counts, and row-manifest availability/truncation.
- Completed Excel batch-group UI should render matched / manual-review / unresolved counts from `excel_intake_progress`. `execution_phase_contract.active_phase_detail` may mirror the same counts for timeline consistency, but frontend logic must treat the structured payload as the contract.
- Excel target-candidate export writes `target_candidates_manifest.json` with the export scope, marker lineage, matched row lineage, and the Excel sidecar review/unresolved rows when present. Full raw workbook export for very large sheets should be a separate streaming/export mode, not the default target-candidate package hot path.

## LinkedIn Stage 1 Progress

`linkedin_stage_1_progress` is the contract for the execution-process counters:

- `current_search_returned_count`: new current-member rows returned by company employees or current-scoped profile search.
- `former_search_returned_count`: new former-member rows returned by former-scoped profile search.
- `all_search_returned_count`: rows whose employment lane is intentionally all/unknown.
- `deduped_candidate_count`: unique LinkedIn candidate population known to this Stage 1 run after URL/name dedupe. This must be at least the known profile-fetch denominator.
- `deduped_profile_url_count`: unique LinkedIn profile URLs known to this Stage 1 run.
- `profile_fetch_required_count`: unique profile URLs that Stage 1 decided need LinkedIn profile detail.
- `profile_fetched_count`: required profile URLs already fetched or available from the registry.
- `profile_queued_count`: required profile URLs still queued/missing/deferred for fetch.
- `profile_failed_retryable_count`: retryable profile-fetch failures.
- `profile_pending_count`: required minus fetched minus unrecoverable.

Required invariants:

- Public Stage 1 counters are lifecycle-backed. Once `job_result_lifecycle` has a validated Stage 1 projection, `/progress`, `/dashboard`, and `/candidates` must render lane counts and the profile denominator from that row. Public-read builders may supplement fetched/queued/retryable status from live registry/workers, but they must not erase or inflate persisted business counters.
- `profile_fetched_count <= profile_fetch_required_count`.
- `profile_fetch_required_count <= max(deduped_candidate_count, deduped_profile_url_count)`.
- When any Stage 1 lane-returned count is present, `deduped_candidate_count` and `deduped_profile_url_count` must not exceed `current_search_returned_count + former_search_returned_count + all_search_returned_count`. A true zero-result current lane is valid, but it cannot be paired with a larger worker-derived denominator in the public business counters.
- `current_search_returned_count`, `former_search_returned_count`, `deduped_candidate_count`, `profile_fetch_required_count`, and `profile_fetched_count` must be monotonic for a job, except a retry/repair may replace a failed job with a new job id.
- Search seed progress must merge aggregate `search_seed_discovery/entries.json` and lane assets such as `search_seed_discovery/current/entries.json` and `search_seed_discovery/former/entries.json`. A partial aggregate file must not hide a completed lane asset.
- A non-empty durable search-seed snapshot must also have a snapshot-level `candidate_documents.json` projection before profile prefetch dispatch can make those URLs visible to local-apply closure. This applies to both worker-owned search-seed recovery and direct Harvest people-search discovery. The projection is a lightweight prerequisite/preview artifact; it must preserve existing richer profile/card fields and must not be used as a reason to redo full candidate artifact materialization on a public read. The ordering matters: incremental search-seed callbacks must project shell candidate rows first, then queue profile prefetch, then reawaken any `local_apply_closure` item waiting on the candidate-document prerequisite. Otherwise a fast profile batch can finish before its candidate rows exist and the workflow falls back to the bounded `waiting_prerequisite` timer, creating a visible finalization tail even though provider scheduling was healthy.
- While profile prefetch is pending, the root snapshot `candidate_documents.json` is the canonical local-apply merge target and must be merge-preserving. A resumed Stage 1 enrichment pass may write a partial `candidate_documents.linkedin_stage_1.json` archive, but it must not shrink or overwrite a broader root candidate-document population produced by roster/search-seed discovery. Final completion may canonicalize/dedupe the root population; pending prefetch may only expand or enrich it.
- Profile worker URLs may fill the denominator only when the search/roster snapshot cannot yet provide the URL set; they must not make the UI show `需补取 LinkedIn Profile` greater than the deduped population.

Frontend wording:

- Show `新发现在职候选人`, `新发现离职候选人`, `经去重得到`, `需补取 LinkedIn Profile`, and `已取回 LinkedIn Profile`.
- Do not show worker counts as a primary product metric.
- If a future API exposes unclassified lane rows, display them explicitly rather than silently adding them to current or former.

Scripted/browser gates:

- Service-level smoke matrices should set `require_no_progress_contract_violation=true` when validating provider-backed workflows.
- This expectation fails closed if the progress observability report is missing, Stage 1 counters regress, result-view lifecycle counters regress, or any explicit progress invariant is violated.
- This gate is intentionally stricter than a report-only metric: the OpenAI Infra failure shape must fail before manual browser testing, not only appear in a timing summary.
- Recovery and board-streaming gates should use `require_no_service_recovery_violation=true` and `require_no_board_visible_projection_violation=true` where applicable. These fail on stuck durable recovery items and on board-visible counts that cannot be explained by a serving projection plus patch log, or by a full `current_snapshot_serving` result view.
- User-visible latency gates should be explicit per scenario: `max_job_to_stage_1_preview_ms`, `max_final_results_to_board_nonempty_ms`, `max_final_results_to_layering_visible_ms`, `max_job_to_board_nonempty_ms`, `max_stage_1_preview_to_final_results_ms`, and `max_global_next_worker_start_gap_ms`. The handoff gap SLO applies to explicit provider-handoff or multi-worker gates; an efficient single merged profile batch should not be split merely to create a next-worker gap metric.
- Smoke must measure board visibility and post-result layering separately. `final_results_to_board_ready_ms` / `final_results_to_board_nonempty_ms` are candidate-board serving metrics: if a board-visible patch made the board non-empty before final results, the final-to-board value is `0ms`. The layering probe may continue polling to its own SLO, but that wait must not inflate board-ready or board-nonempty UX metrics.
- `require_layering_visible_after_results_within_slo=true` must use the scenario's declared `max_final_results_to_layering_visible_ms` as its layering probe window. Hidden short probe deadlines are invalid because they can false-fail a backend that completes layering inside the product SLO. A direct-finalization run may report `board_runtime_state.phase=post_result_layering`, `publication_status=complete`, complete served/display-ready counts, and `layering_status=deferred|scheduled`; that is an explicit post-result tail contract and must not be treated as board-serving failure.
- Full-local-reuse / `reuse_snapshot_only` gates should set `max_progress_payload_bytes` and `require_no_active_stage1_for_full_local_reuse=true`. A local-reuse run must not expose active LinkedIn Stage 1 wording, `profile_work_pending=true`, or delta profile progress as applicable.
- Public `/progress` is a polling contract, not an artifact export. It must project allowlisted counters/status/timing, compact list-heavy fields into counts such as `deferred_url_count`, and omit raw provider URL lists, baseline-selection proof trees, confidence-policy payloads, and `summary_path`. The OpenAI Reasoning reuse-snapshot scripted fixture currently uses a `50 KB` max payload budget and observes about `10.6 KB` locally.
- The OpenAI Infra lane-skew fixture is the canonical Stage 1 coherence gate. It reproduces a valid zero-result current lane plus a former-only delta and requires the latest public counters to stay `current=0`, `former=77`, `all=0`, `deduped=77`, `profile_required=77`, and `profile_fetched=77`. A worker/provider URL queue larger than the lane-returned population must be reported only as technical queue metadata, not as the user-facing denominator.

## Result View Lifecycle

`result_view_lifecycle` is the contract for candidate-board streaming:

- `baseline_snapshot_id`: baseline snapshot served immediately for baseline+delta workflows.
- `current_snapshot_id`: snapshot being built by the current run.
- `served_snapshot_id`: snapshot currently backing the board API.
- `serving_projection_id` or equivalent: job-scoped serving projection that may combine a baseline generation with ordered delta patches before full current-snapshot compaction.
- `serving_projection_phase`: for example `baseline_only`, `patch_applying`, `patch_serving`, `snapshot_compacting`, `current_snapshot_serving`.
- `baseline_candidate_count`: candidate rows in the baseline board.
- `served_candidate_count`: candidate rows currently served by the backend result view.
- `expected_candidate_count`: final candidate count expected for the current board lifecycle.
- `delta_profile_required_count`: denominator for current run's profile delta.
- `delta_profile_fetched_count`: profile delta fetched.
- `delta_profile_materialized_count`: profile delta rows visible on the candidate board. This is a board-serving/materialization contract, not a profile-richness completeness metric; it must come from backend materialization state, an explicit materialization patch, or the served current snapshot, not from frontend array length.

## Board Runtime Contract

`board_runtime_state` is the canonical backend-driven projection of the membership/readiness owners for `/progress`, `/dashboard`, `/candidates`, and `/board-patches`. Exact visible membership owns the board header and main sync `N/N`; independent owners provide profile/card/capture readiness, facet readiness, and filter scope. Frontend board state should prefer it over `result_view_lifecycle` whenever it exists. `result_view_lifecycle` remains the lower-level serving-view contract for delta/current-snapshot repair and diagnostics, but it is not a fallback total source once a canonical projection link exists.

Cross-endpoint parity:

- Public reader canonical projection v1: `/progress`, `/dashboard`, `/candidates`, `/board-patches`, and `/results` build lifecycle and board-runtime state from the same exact membership revision. Endpoint-specific page payloads may contribute rows, offsets, limits, and filtered counts only; they cannot upgrade/downgrade the membership revision, `facet_summary_scope`, profile/card/capture counters, lifecycle state, publication tier, or sync copy.
- The same comparable `board_runtime_state` fields must be exposed by `/progress`, `/dashboard`, `/candidates`, and `/board-patches`: job id, result mode, phase/publication status, exact membership count/scope/revision, served/published/display-ready counts, row hydration target, independently scoped profile/card/capture counters, publication tier/sequence/watermark, facet/layering status, sync/profile/card status text, and `filter_contract`.
- `/progress.progress.counters.result_count` is the frontend-visible canonical visible-member count, not the raw acquisition-source row count and not the usable-card count. Raw source rows may be preserved in audit artifacts, but membership publication must dedupe to the same member-key population served by `/candidates`. A raw discovery shape such as `120 current + 25 former = 145 raw rows -> N=140 canonical candidates` publishes main sync `140/140`; card detail is independently `C/140`, and profile readiness/fetch uses its owned scope rather than being forced to `140/140`.
- Terminal lifecycle promotion mirrors the exact membership token and `N`; Stage 1 profile-required/deduped counts may remain diagnostics but cannot prove, inflate, or repair the canonical board population.
- Terminal lifecycle accounting is a write-side completion contract. When a workflow is persisted as `jobs.status='completed'` and `jobs.stage='completed'`, an existing `job_result_lifecycle` row must be marked `phase_status='terminal'` by the completion writer. Public readers may render terminal invariants but must not be the owner that repairs active lifecycle rows for completed jobs.
- Endpoint-specific payloads may differ in candidate rows, patch rows, diagnostics, or pagination metadata. They must not disagree on the canonical board business state. A missing `board_runtime_state` from any of the four endpoints is a contract failure for provider-backed workflow smoke.
- Python scripted smoke must use `require_board_runtime_state_cross_endpoint_parity=true` for provider-backed streaming/reuse cases. This gate compares the public endpoints directly; it does not recompute counters from `linkedin_stage_1_progress`, `result_view_lifecycle`, patch rows, or frontend cache state.

Post-profile public projection:

- `linkedin_stage_1_progress.profile_fetched_count` means profile URL terminal success or profile detail available in the registry for the Stage 1 required URL set. It does not mean the card is already visible on the candidate board.
- `result_view_lifecycle.delta_profile_fetched_count` is the event-time profile fetched denominator/numerator for the current board lifecycle. It must be derived from registry/lifecycle proof, not frontend row arrays.
- `local_apply_closure` item completion / `inline_incremental_ingest` is the backend handoff between fetched profile detail and board-visible publication. It is not directly user-facing copy, but `service_metrics.local_apply_backlog` must expose it so smoke/browser reports can explain why fetched profiles are not visible yet.
- `board_visible_delta_apply` completion and `job_board_visible_patches` publication are event-time evidence inputs. A projection publication may use them to advance exact visible membership and independently advance card/profile/capture facts, but a patch count is not itself the canonical `N`, `C`, or `P` until the owner publishes a revision-bound exact projection.
- `current_snapshot_row_shell_overlay` is the early row-publication contract for a terminal candidate list whose profile workers or post-profile queues are still running. It may set `served_snapshot_id`, `served_candidate_count`, `expected_candidate_count`, `serving_projection_id`, and `serving_projection_phase`, but it must keep `phase/state=current_snapshot_materializing` and must not advance `delta_profile_fetched_count`, `delta_profile_materialized_count`, or `delta_profile_board_visible_count`. It exists so baseline/candidate-list rows can be browsed while profile/card enrichment continues.
- Row-shell publication is a Stage 1/candidate-source terminal event, not a Stage 2 final retrieval side effect. Once the discovery lane has terminal candidate documents and the direct asset-population context can resolve a snapshot-authoritative source, the runner dedupes raw source candidates into a canonical public board source, publishes a compact job-scoped row-shell overlay and result view, records `serving_projection_phase="current_snapshot_row_shell_overlay"`, and then returns control to profile/local-apply/board-visible/finalization queues.
- Row-shell reuse patches are cumulative evidence within their patch generation. A profile/card batch that arrives after row-shell publication must persist the current-patch facts and the cumulative ledger, but only the canonical projection owner may reduce them into exact `C/N`. Same-token tail patches cannot erase earlier facts; a newly authoritative exact publication may legitimately correct the aggregate in either direction or to zero.
- Direct finalization must reuse the existing serving projection when its exact membership revision is already complete for the same job/snapshot. Reuse proof compares the canonical visible-member set/revision, not raw lifecycle counts or card completeness. A repair writer may build a replacement projection when proof is absent; public readers do not fall back to that overlay while the replacement is non-exact.
- Post-profile SLO `all_profiles_fetched -> all_cards_visible` is a correlation metric only for a declared profile-delta scope. It must compare owned profile-terminal evidence with owned card-ready evidence for that same scope/revision. It is not a global inequality and must not synthesize card readiness from profile completion or vice versa.
- `board_runtime_state.display_ready_candidate_count` is the compatibility view of exact card-ready `C`, used for card detail `C/N`. Exact visible membership `N` is the main `候选人同步` numerator and denominator; pure row shells count in `N` even when `C=0`.
- `board_runtime_state.profile_fetch_status_text` comes from profile fetch/registry/lifecycle evidence. `board_runtime_state.card_materialization_status_text` comes from exact card-readiness evidence and uses `C/N`. They share a membership revision only for comparison and must not be derived from each other.
- Public profile/card counters have independent invariants: each owned membership-scoped count is in `0..N` for the same exact revision. There is intentionally no `card_materialized <= profile_fetched`, `card_ready <= profile_ready`, or reverse ordering rule.
- For baseline+delta workflows, global card/profile/capture counters must not be treated as delta counters. Exact delta values require owner-published delta scope and identity; subtracting a baseline floor is not sufficient. In particular, `explicit_profile_capture_candidate_count` is never derived from profile/card counts.
- `board_runtime_state.sync_note_lines` is the canonical user-visible candidate-sync copy. It is emitted by the backend projection writer in stable order (`candidate_discovery`, `profile_fetch`, `card_materialization`) and frontends must not prepend recall/intent-match text into the same business progress line. Intent-match summaries can be shown elsewhere as filter context, not as provider/card progress.
- Once the authoritative resolver returns a canonical exact projection publication, it outranks legacy lifecycle/asset/patch summaries for membership and readiness. Within the same token, stale partial patches cannot erase richer owned facts. Unequal tokens cannot be merged or ordered; the client re-resolves and accepts the newly pinned exact snapshot even when `N`, `C`, or `P` decreases or becomes zero.
- Board-runtime freshness compares canonical-vs-legacy publication tier, then requires `projection.membership_revision` equality for direct merge. `partial_patch` sequence orders patch replay only within its generation. Same-token completeness can break ties; unequal or missing tokens invalidate caches and fail closed until a pinned re-read. Neither token text, `updated_at`, sequence, nor count magnitude orders canonical membership.
- `board_runtime_state.phase` / `result_view_lifecycle.serving_projection_phase` express serving-publication state. `results` / `serving_finalized` means the board API has a coherent projection and stable counters; it does not require post-result layering or full artifact compaction to be finished.
- `board_runtime_state.layering_status` is post-result layering/facet status. It may be `deferred` or `scheduled` after exact membership publication when normalized artifacts or the search index are queued. This state is paired with complete exact membership `N/N`; card detail may remain `C/N`, and public facets remain pending/unavailable until the search-index owner finalizes. Layering must not rewrite profile, card, capture, or membership counts.
- Public-read repair may promote an otherwise results-ready workflow to `completed` only when no active workflow owner lease exists. A live `workflow_job_lease` means the runner/recovery owner still controls retrieval, layering, finalization, and terminal publication; `/progress`, `/dashboard`, and `/candidates` must render state without persisting terminal completion on the owner's behalf. Stale, expired, or proven-dead local leases remain repairable through the recovery path.
- Scripted smoke must expose `service_metrics.post_profile_completion` for provider-backed profile work. The report owns URL terminal-state leak count, event-level callback elapsed time, `profile_file_visible -> board_patch_visible`, and `all_profiles_fetched -> all_cards_visible` SLOs. These are quality gates, not frontend display hints; a failure means the backend post-profile state machine is not coherent enough for manual browser testing.

Candidate sync display rules:

- A baseline+delta workflow must never serve a raw delta-only snapshot as the final `asset_population` board. If `served_snapshot_id` is the current delta snapshot but `baseline_snapshot_id` exists and the served count is below the baseline count, the backend must either serve the baseline view or repair to a job-scoped baseline+delta overlay until the durable current materialization/repoint completes.
- The ideal serving state is a continuous projection, not a complete snapshot switch. Public board APIs may serve baseline generation + ordered delta patches + row-level materialization state while full current snapshot/retrieval/index compaction catches up in the background.
- Snapshot repoint/compaction is not required before a fetched/applied delta row becomes visible. If a row is safe to expose, the lifecycle should advance `delta_profile_materialized_count` / board-visible count through the projection and keep `serving_projection_phase` honest.
- Completed-job Harvest profile tail has the same boundary. If a serving result view / board projection already exists and the recovered work only adds profile detail for known candidate ids, local-apply closure completes the `board_visible_profile_delta` contract: synchronize the candidate delta into the control plane, publish the durable board-visible patch, and write `inline_incremental_ingest`. It must not synchronously run full snapshot normalization, retrieval refresh, or layering refresh. Full snapshot compaction is always owned by `snapshot_full_materialization` when scheduled; running workflows hold the item in `waiting_workflow_completion` until final workflow publication releases it to `queued`. If changed candidate ids cannot be resolved, the public contract is `snapshot_full_materialization_queued`, not a synchronous fallback.
- Full `current_snapshot_serving` is itself the serving projection. It does not require a patch log, but the lifecycle must still persist `serving_projection_id`, `serving_projection_phase='current_snapshot_serving'`, and board-visible delta counters when background materialization advances.
- Board-visible delta patches are durable serving-projection events. `job_board_visible_patches` owns ordered/idempotent patch replay; `job_result_view.metadata` and `job_result_lifecycle.metadata` are mirrors for API/debug context and must not be the only source needed to accumulate follow-up patches.
- `job_board_visible_patches.patch_id` is a compact deterministic id, not a serialized candidate-id list. Candidate-id replay data stays in JSON payload columns; otherwise large pressure chunks can fail at the Postgres primary-key/index layer before publication.
- Patch-log polling uses `latest_sequence_index` as the primary cursor plus `latest_published_at` as compatibility context. Timestamp-only cursors are invalid because multiple patch rows can share the same provider/materialization timestamp while sequence still advances.
- Patch-log payloads must expose card-quality counts for each patch: `display_ready_candidate_count`, `profile_detail_candidate_count`, `explicit_profile_capture_candidate_count`, `preview_candidate_count`, `needs_profile_completion_candidate_count`, `low_profile_richness_candidate_count`, and `quality_fields_available`. The frontend may use these to decide whether to refresh dashboard rows, but it must still read rows through `/dashboard` / `/candidates`.
- Patch-log card-quality counts are event-time facts. Writers must freeze `display_ready` / `profile_detail` / `preview` / `needs_profile_completion` counts when the patch is published; public readers must not recompute earlier patch quality from mutable final snapshot overlays or a later profile registry state. This applies equally to small-company live roster and large-company baseline+delta runs.
- Final/direct asset-population writers must merge already-published event-time board-visible rich records before rewriting the job-scoped `*.asset_population.json` overlay. Full snapshot compaction may add rows and artifact-local facet/retrieval inputs, but those facets are diagnostic until `projection_person_search_index` publishes the revision-matched public product. Compaction cannot overwrite richer profile/card fields from partial patches with shell rows or become a public count fallback.
- When final asset-population publication reuses a completed board-visible projection, the final summary `candidate_source.candidate_count` / `total_matches` / `returned_matches` must match the serving projection count, not an older company-snapshot or generation-patch source count. The older source count may be retained only as diagnostic metadata such as `pre_serving_projection_candidate_count`.
- A live-roster run and a baseline+delta run must use the same board-runtime semantics. The only difference is the denominator shape: live roster reports `candidate_discovery/profile_fetch/card_materialization` over the run population; baseline+delta reports profile/card materialization over `delta_profile_required_count` while the main board sync includes the already-serviceable baseline.
- Stage 1 terminal detection is registry-owned. `src/sourcing_agent/workflow_event_response.py` maps both scoped-search (`search_seed_discovery_query` durable items) and live-roster (`live_roster_discovery_lane` durable items written by company-roster apply) into one `linkedin_stage_1` discovery-lane contract. Promotion requires no non-terminal matching discovery workers and at least one same-snapshot terminal durable item. Worker apply markers are audit evidence only and must not directly promote denominators. New workflow shapes must extend that registry instead of adding another branch in public lifecycle writers.
- Board-runtime freshness rule: a revision-matched `projection_person_search_index` facet product plus completed layer assignment is canonical layering completion for the served board. It may outrank same-token stale `post_result_layering` / `running` mirrors; it cannot be merged across unequal membership tokens.
- `result_view_lifecycle.outreach_layering_status` is an event-time lifecycle field only. Public reads may render `board_runtime_state.layering_status` from the current served facet/layer summary, but they must not backfill or mutate `job_result_lifecycle` from a dashboard/progress/candidates read.
- Global layering generation is durable projection work, not request-time public-reader repair. `workflow_commands(command_type='projection.facet_layering.build')` owns bounded layer assignment over pinned canonical members and then enqueues the revision-fenced `projection_person_search_index` build. It does not own or directly publish public facet truth: only search-index finalization may publish exact facets for the matching `projection.membership_revision`. Historical `job_materialization_items(item_kind='projection_facet_layering_build')` rows may be converted by the migration adapter, but legacy job overlays are not executable layering sources. Smoke pressure cases that require global filters/layering must drain both owners and require revision-matched index evidence; row serving may be ready earlier while facets remain pending/unavailable.
- Board-visible delta apply work is a typed durable command before it is a patch. Normal path execution payload lives in `workflow_commands(command_type='projection.board_visible_patch.publish')`, owned by the board-visible patch publisher. Historical `job_materialization_items(item_kind='board_visible_delta_apply')` rows may appear only as report-visible migration adapter references and must not become the normal source of execution payload. `job_board_visible_patches` records only successful serving-projection publications. A transient overlay writer failure must leave a retryable command that the recovery service can claim on a later tick without another provider webhook.
- Board-visible chunks must not fragment a normal completed profile batch into many tiny overlay rewrites. The default chunk resolver keeps provider-batch-sized waves together (`BOARD_VISIBLE_DELTA_APPLY_CHUNK_SIZE`, default `256`) and only expands toward `BOARD_VISIBLE_DELTA_APPLY_TARGET_CHUNK_COUNT` / `BOARD_VISIBLE_DELTA_APPLY_MAX_CHUNK_SIZE` for unusually large waves. This preserves streaming at profile-batch granularity while preventing pressure scenarios from spending recovery time repeatedly rewriting the same baseline+delta overlay.
- Partial board-visible overlay updates are record-level serving-projection merges. Once a verified partial overlay exists, follow-up `board_visible_delta_apply` must reuse the existing overlay records by stable member key and merge only the current patch's delta records. It must not deserialize every existing row into a `Candidate`, re-run full baseline normalization, scan the profile registry for the whole board, or rebuild thematic facets as part of the user-visible patch. A first partial patch may write a compact bootstrap overlay with `overlay_write_mode='full_rebuild'` and `overlay_fast_path_used=true`; that is not a fallback unless `overlay_fallback_reason` is present or the fast path was not used.
- Patch identity and replay payload are separate contracts. Indexed identifiers (`patch_id`, `job_id`, `snapshot_id`, sequence fields) must stay compact and deterministic. Candidate-id replay data belongs in JSON payload columns such as `candidate_ids_json` / `cumulative_candidate_ids_json`, not in a primary key, unique key, or btree-indexed text field. Large pressure chunks must therefore be able to persist thousands of replay candidate ids without increasing indexed row size.
- Full snapshot compaction is also a typed durable command before normalized artifacts exist. Normal path execution payload lives in `workflow_commands(command_type='snapshot.compaction.run')`, owned by `snapshot_full_materialization`; `job_materialization_items(item_kind='snapshot_full_materialization')` is migration-era evidence only when an explicit adapter reference is present. The `background_snapshot_materialization` summary field is a UI/compatibility/backfill mirror and must not be a normal recovery source. Public reads and service recovery scans must not create or run this work from summary-only state. Job-scoped recovery must report open snapshot compaction commands as background materialization backlog, not daemon-owned sidecar work; the sidecar owns provider recovery, profile refill, local apply, board-visible apply, and workflow resume only.
- Background full snapshot compaction must not republish completed workflow results. After canonical final results are published, `snapshot_full_materialization` may synchronize normalized artifacts, publish a full-snapshot board-visible serving patch, and update only the `background_snapshot_materialization` status mirror. It must not call retrieval refresh, append another `Workflow completed` publication, rewrite `stage_2_final`, or overwrite the final result artifact. Missing final publication is a separate repair contract, not a side effect of compaction.
- Post-Stage-1 direct asset-population finalization is allowed only when the current snapshot is already a snapshot-authoritative candidate source. In that state, `normalize_asset_snapshot` and `build_retrieval_index` are not user-visible finalization prerequisites: the workflow records them as skipped/deferred acquisition tasks, publishes final results from the authoritative candidate source, and releases `snapshot_full_materialization` only after workflow completion. If the candidate source is not authoritative, those tasks remain blocking acquisition work.
- Runner terminal-proof bridge: the main workflow runner may treat `enrich_linkedin_profiles` as completed from an existing terminal Stage 1 artifact only when `_acquisition_task_checkpoint_reusable(...)` is true and the same post-profile resume barrier used by recovery is clear. A terminal `candidate_documents.json` is not enough if `local_apply_closure` or `board_visible_delta_apply` post-profile daemon work is still queued, running, retryable, or waiting for prerequisites; in that case the runner must stay blocked instead of re-running provider tasks or advancing to finalization.
- Background snapshot materialization scheduling is queue-only. Workflow completion may enqueue/release a `snapshot_full_materialization` item and mark the summary mirror `scheduled`, but it must not start an ad-hoc background thread that races the active workflow job lease. The materialization item processor owns only snapshot compaction; it must not detour through generic completed-workflow reconcile branches such as outreach layering before normalized artifacts exist.
- Snapshot-full queue state must be observable independently of summary mirrors. `GET /api/jobs/{job_id}/materialization-items` is the read-only diagnostics source for smoke/operator reports, and `service_metrics.snapshot_full_materialization_queue` must expose item count, backlog, retryable count, ready retry count, stale running count, terminal failures, status/phase counts, and error samples.
- Local apply closure must be observable independently of provider duration and full-compaction backlog. A worker that has `output.inline_incremental_apply` but no matching `output.inline_incremental_ingest` is applied-not-ingested work. `service_metrics.local_apply_backlog` must expose count, stale count, age summary, worker/recovery kind breakdowns, samples, and bottleneck entries so smoke reports can distinguish provider output already applied locally from downstream closure failures.
- Local apply backlog recovery is durable-item owned. A drain may claim only `job_materialization_items(item_kind='local_apply_closure')` and resume downstream local closure for the item's owned worker ids; it must not re-execute the remote provider actor or re-run snapshot apply when the existing `inline_incremental_apply.snapshot_id` already matches the worker snapshot. Successful drain lease release must not write a `last_error`.
- `local_apply_closure` items are the durable bridge for that recovery. `inline_incremental_apply` writes must enqueue a deterministic `job_materialization_items(item_kind='local_apply_closure')` row; `inline_incremental_ingest` writes must complete the matching item. The worker marker remains the collector gate, but pending closure/retry/stale-running state must be visible as item state rather than only as a worker-output scan.
- Recovery drains `local_apply_closure` in bounded units. A normal service tick may split same-job/snapshot/worker-kind closure groups by `LOCAL_APPLY_BACKLOG_GROUP_LIMIT` and stop after `LOCAL_APPLY_BACKLOG_PHASE_BUDGET_MS`, leaving unclaimed items durable for the next tick. This is intentional: local apply closure must not become a 20s+ monolithic recovery phase that hides provider callback or board-visible progress behind one long synchronous section.
- Recovery aggregate ticks are bounded units too. `RECOVERY_TICK_TOTAL_BUDGET_MS` caps a whole recovery pass; when exhausted, the daemon must set `next_tick_requested=true`, leave the remaining worker/local-apply/board-visible/finalization work durable, and yield. Service metrics must expose `recovery_tick_budget_exhausted_count`, `budget_yield_next_tick_requested_count`, `cooperative_budget_yield_count`, `budget_yield_contract=cooperative_recovery_budget_yield`, `phase_candidate_count`, `phase_candidate_count_max`, and `local_apply_candidate_per_second` so a pressure run can show whether slowness is provider latency, candidate volume, a clean cooperative yield, or an unbounded synchronous phase. A clean budget yield requires no missing/failed/slow/unexpected phase and no legacy bridge; Pre-Manual Signoff records it as `recovery_cooperative_budget_yield`. Missing `next_tick_requested` or dirty owner evidence keeps the budget yield report-visible as attention/warning.
- When a tick already consumed terminal worker evidence or submitted profile-refill provider work, `durable_work_handoff_yield=true` is a separate cooperative yield: the same tick must not also drain local-apply, board-visible, or full snapshot work. When a ready board-visible item exists, recovery publishes that bounded visible unit before claiming more local-apply work; local apply and board-visible publication must not be serialized into one recovery tick. If the same recovery report has no missing/failed/slow/unexpected phases, no legacy bridge, and no tick-budget exhaustion, service metrics must report `cooperative_handoff_yield_count` and Pre-Manual Signoff must record `recovery_cooperative_handoff_yield` as a passed gate. If the recovery contract is dirty, the yield stays diagnostic and the dirty owner signal remains blocking.
- Finalization readiness must not wait for background-only compaction/layering. The user-visible readiness gate is canonical board-visible projection plus post-profile SLO evidence. `max_stage1_terminal_to_finalization_start_ms` is profile-aware: when provider-backed profile work is still legitimately running after Stage 1 terminal proof, the gate excludes remote profile wait and measures `profile_terminal_at -> first_finalization_started_at`; otherwise it measures `linkedin_stage_1.completed_at -> first_finalization_started_at`. The report must expose the raw Stage 1 delta, `profile_terminal_to_first_finalization_start_ms`, `finalization_start_gate_ms`, `finalization_start_gate_source`, and `finalization_lag_evaluation_ms`; service metrics and signoff bottlenecks must evaluate the provider-wait-excluded value, not the raw preview-to-final wall clock. Full snapshot compaction and layering remain separately observable optimization/background phases. Healthy queued/running `snapshot.compaction.run` work is a background-maintenance gate, not a manual-handoff warning; retry, stale-running, or terminal-failed compaction remains blocking owner evidence.
- A coalesced closure drain must preserve per-worker ownership. If a claimed group mixes workers that already have `inline_incremental_apply` with workers that still need Phase A apply, existing markers are replay-only evidence and must not be overwritten by the new apply result. The downstream board-visible delta uses the union of replayed candidate ids and newly applied candidate ids; a `local_apply_closure` item may not complete with metadata whose applied worker ids exclude its owned worker ids.
- Harvest-profile local apply closure does not own next-submit scanning. After a profile batch is ingested, the closure path must reuse the lightweight `provider_submit_deferred_to_refill_daemon` signal and proceed to board-visible publication; it must not call `queue_background_profile_prefetch(...)` / registry replan itself. This prevents profile-file-to-board visibility from being blocked by scheduler scans.
- Profile tiny-tail coalescing timers are durable profile URL scheduler state, not provider workers. Fresh high-volume `1`-`5` URL tails must write `linkedin_profile_registry.refill_queue_state='deferred_coalescing'` with `refill_not_before_at`; refill selectors may only return those rows after the deadline. A `waiting_profile_coalescing` worker is legacy scheduler pollution and must not be created or recovered as a normal path.
- Profile retry waits are durable profile URL scheduler state, but only for workflow-owned rows. `status='failed_retryable'` records profile lifecycle evidence; it becomes daemon-drainable scheduler work only when `refill_queue_state='retry_wait'`, `refill_not_before_at`, `source_jobs`, and `last_snapshot_dir` are present. Maintenance/offline failures without workflow scope must not create orphan retry items.
- Profile retry waits are isolated from normal actor-slot packing. Retry dispatch is gated by normal-wave closure, not by a loose "normal ready queue is empty" heuristic. Refill selectors must exhaust normal ready states (`deferred_budget`, `deferred_coalescing`, expired `dispatch_reserved`, expired `dispatch_claimed`) before selecting `retry_wait`; `queue_background_profile_prefetch` may read `retry_wait` only when the current event has no new candidate URLs, there are no normal open URL scheduler rows for the same `source_job + snapshot_dir` (`deferred_budget`, `deferred_coalescing`, `dispatch_reserved`, or `dispatch_claimed`, ready or not-yet-ready), and no first-attempt `planned_dispatch` item is still waiting for item-level terminal state. The default retry budget is one retry per URL; after that, the registry row becomes `unrecoverable` and leaves the scheduler queue.
- Profile actor-slot packing is item-count and source-shape based. `50` is the minimum normal actor-slot target and sub-tail boundary, not a hard chunk size for every ready set. Search-driven complete ready sets with `51..HARVEST_PROFILE_PREFETCH_DURABLE_UNIT_MAX_URLS` URLs may remain one durable provider envelope so small shards such as a 120-profile former lane are not forced into 50/50/20. Company-roster-heavy waves with multiple available actor slots must instead split into normal actor-slot envelopes before opening a large single envelope, so live-roster runs do not leave provider capacity idle. Larger ready sets are balanced up to the durable actor-envelope cap (`HARVEST_PROFILE_PREFETCH_DURABLE_UNIT_MAX_URLS`, default `200`); waves above `400` explicitly pack toward that cap to amortize provider startup latency. The `8` envelope setting is a soft planning target, not permission to shrink a 529/600 URL wave into many 67/75 URL envelopes. Small retry-only envelopes are allowed only when the batch plan records `retry_isolation=true`; sub-50 normal envelopes require an explicit coalescing/low-volume/queue-quiescent reason.
- Worker-backed profile prefetch has one scheduling entry point: `MultiSourceEnricher.queue_background_profile_prefetch(...)`. Acquisition/full-roster/scoped-search enrichment may append candidates or URLs into this contract, but it must not independently build batch plans, open ThreadPool submitters, or call Harvest profile batch workers directly from `enrich(...)`. `_execute_harvest_profile_batch_worker(...)` is the provider-envelope submit/resume primitive used by the scheduler and worker recovery, not a second planner.
- When worker-backed prefetch reports `completed` because local raw cache already satisfies the request, enrichment may hydrate profiles only from the registry/snapshot cache. It must not call `fetch_profiles_by_urls(...)` as a synchronous fallback in the worker-backed workflow path; otherwise a cache-hit run can silently bypass scheduler locks, provider-mode gates, and profile scheduler observability.
- Company-asset completion and enrichment maintenance follow the same cache-only hydration contract. If a requested profile is missing from registry/snapshot cache, the writer must enqueue `linkedin_profile_registry` work under a scheduler-owned `source_job + snapshot_dir` scope and return `profile_completion_scheduler_queued` / equivalent pending evidence. Non-main workflows must not call the live Harvest profile connector as a foreground "repair" fallback, because that would bypass runtime isolation, provider-mode reports, actor-slot accounting, retry-wave isolation, and Pre-Manual Signoff gates.
- Profile replan is scoped and non-invasive. Append-trigger replans over `source_job + snapshot_dir` may include not-yet-ready `deferred_coalescing` rows so near-ready probe shards can form a full normal actor envelope; daemon/timer refill must still respect `refill_not_before_at`. Append-trigger replans must not ignore `dispatch_reserved` / `dispatch_claimed` timers, because those rows guard an active local submit path rather than a coalescing window. Replan may resize only unsubmitted scheduler-owned normal rows and must not touch provider-owned `planned_dispatch`, fetched, unrecoverable, or retry-owned rows. The "8 envelopes" rule is a target for the current unsubmitted normal set and service report, not a global workflow cap, historical envelope budget, or reason to underfill durable actor envelopes.
- Profile dispatch ownership must not conflate "selected", "reserved", "claimed", and "provider-owned". `dispatch_reserved` is a short-TTL scheduler reservation written under the per `source_job + snapshot_dir` lock for active chunks selected by a plan; it prevents duplicate same-wave planning while provider slot / worker begin is attempted, and expires back into daemon-drainable normal work if the process dies. `dispatch_claimed` may be written only after provider limiter/slot confirmation and immediately before local worker/provider submit. `planned_dispatch` may only be written after a remote provider run/worker owns the URLs and must carry the remote envelope identity (`refill_owner_worker_id`, run id, dataset id, payload hash when available). It is not a ready queue state: normal selectors skip it, and retry selectors use it only as a quiescence barrier. Provider-slot backpressure or begin-worker failure must return URLs to `deferred_budget`, not leave them in `dispatch_reserved`, `dispatch_claimed`, or `planned_dispatch`. Fetched/unrecoverable completion clears `refill_queue_state` and writes terminal status on the same registry item; `planned_dispatch` without a remote owner is a scheduler violation, not a valid wait state.
- Profile completion callbacks must not run direct refill. They emit a lightweight `provider_submit_deferred_to_refill_daemon` signal and continue to local apply / board-visible work. Registry scan, replan, claim, limiter acquisition, and provider submit belong exclusively to the runtime-owned profile-refill daemon. Remote provider event recovery should enable that daemon in the same recovery tick after worker callbacks return, but the callback itself must not spawn refill threads, wait on registry scans, submit providers, parse raw profile payloads, run full snapshot materialization, or perform unbounded candidate/artifact work.
- Profile scheduler critical sections are single-writer per `source_job + snapshot_dir`. PG deployments must use a short transaction-scoped try-advisory lock for registry replan/submit-claim work; if the lock is busy, the caller must return `profile_prefetch_scheduler_lock_busy` and yield to a later tick rather than blocking. No provider submit, raw profile parsing, local apply, board-visible patch, or full materialization may run while holding that lock. SQLite's in-process lock is test compatibility only and must not be treated as production parity.
- Profile batch partial success is item-level. A successful URL becomes `fetched` and leaves the scheduler queue immediately; only unresolved or failed URLs become retryable items. A normal batch's URL state must be recorded before retry-wave dispatch can start for that snapshot. Retrying the whole original provider batch or inserting retry URLs ahead of unfinished normal-wave scheduler/provider-owned items violates the profile scheduler contract.
- `event_level_efficiency.profile_scheduler_contract` is the canonical smoke/signoff gate for the profile scheduler. Required provider-backed profile runs must expose the report and have `violation_detected=false`. The report makes the following blocking: small normal batch below the target/min non-tail size without allowed reason, missing batch-size contract, retry mixed with normal open rows, same-wave ordinal overtake, slot refill underfill with deferred backlog, required non-PG advisory lock, ownerless `planned_dispatch`, and terminal queue-state leaks.
- Remote-provider event lag gates are keyed by actionable terminal evidence, not by every observer source. For one provider run, watcher/webhook/poll may all report the same terminal state; only the first durable terminal marker may count toward `actionable_remote_to_local_event_lag_ms` and `remote_to_local_marker_lag_ms`. Later same-run events are duplicate audit (`received_in_flight` or `received_late`) and must not make a strict smoke fail if the first terminal marker arrived within SLO.
- Pre-Manual Signoff also blocks provider-backed profile runs when `service_metrics.post_profile_completion` is missing or incomplete. Required sections are `url_terminal_state_recording`, `event_level_callback`, `profile_file_visible_to_board_patch_visible`, and `all_profiles_fetched_to_all_cards_visible`; final manual browser testing must not start from a smoke run lacking these reports.
- Provider search retry state must be structured before it blocks the workflow. Search-seed query summaries may mirror `zero_result_retry`, but acquisition and progress contracts should consume `provider_retry_items`. Terminal Harvest people-search zero-result exhaustion is projected at event time into `job_materialization_items(item_kind='provider_search_retry')` with `status='failed'` and `phase='terminal'`; it is not a normal zero-result lane and not a public-read inference. Future delayed provider retries should use the same item kind with queued/deferred/retryable states instead of adding another summary parser.
- Provider search retry queue state must be reported from durable items. `service_metrics.provider_search_retry_queue` exposes backlog, retryable, ready retry, terminal failed, stale running, provider/retry-type counts, query samples, and error samples. Smoke/browser reports should use that queue metric for guardrails; `incomplete_provider_query_count` is a legacy compatibility count, not the owner of retry state.
- Result-view repair is a serving publication event, not a public-read responsibility. It must use already-existing baseline and delta `candidate_documents` or an existing overlay, and must not trigger full candidate artifact materialization/retrieval-index rebuild from `/dashboard`, `/progress`, or `/candidates`. It also must not synchronously re-derive expensive thematic facets for the whole overlay; preserve existing candidate fields and defer heavier enrichment to materialization workers.
- If the current workflow snapshot already has a candidate document population at least as large as the baseline, completed workflow reconcile should repoint the result view to the current `candidate_documents` instead of constructing a temporary overlay. Overlay repair is for true delta-only snapshots whose served count is below the baseline.
- Public reads may validate and report stale or unrepaired serving state, but they must not be the normal convergence path for baseline+delta result-view repair. A repaired result view should carry `metadata.repaired_by='completed_workflow_reconcile'` or another explicit event-time owner, not an implicit dashboard/candidate-page repair marker.
- Running public reads must not repoint a stale serving view to a newer current workflow snapshot. If `/dashboard`, `/progress`, or `/candidates` detects that stage/job summary state is ahead of the stored serving view, it may report `metadata.serving_publication_gap.status='pending_event_time_publication'`, but the result-view update must come from the event-time publisher or durable board-visible apply item.
- Smoke/runtime reports must expose `service_metrics.serving_publication_gap` for that diagnostic. Required signals: `gap_present`, `stale_gap_present`, `age_ms`, `served_snapshot_id`, `current_snapshot_id`, and `threshold_ms`. Production-hard scripted matrices should set `require_no_serving_publication_gap=true` and a bounded `max_serving_publication_gap_ms` so missing event-time publishers fail as service SLO violations.
- Completed authoritative-registry result-view repair is also event-time owned. Retired/legacy `sqlite_store` or incomplete completed-job result views must be repaired by completed workflow reconcile (`authoritative_registry_result_view_repair`) before public result reads; `/dashboard`, `/progress`, and `/candidates` must not publish that repair themselves.
- Completed final/current workflow snapshot publication is event-time owned. If a completed job summary points at a materialized current snapshot while the stored result view still serves a stale baseline/legacy snapshot, completed workflow reconcile (`current_snapshot_result_view`) must publish the serving view and lifecycle row before public reads consume it.
- A stale `asset_population_overlay_path` alone is not enough to make the backend serve an overlay. Authoritative result views need a valid patch contract; otherwise public reads must serve the authoritative normalized snapshot or fail closed with `public_serving_artifact_missing`. They must not fall back to sibling/root `candidate_documents.json` when normalized artifact files are incomplete. Raw candidate docs are repair/backfill/acquisition evidence only.
- A repair overlay must preserve the already-served baseline board row count and order. Member-key matching may update or remove matching baseline rows based on delta evidence, but it must not dedupe or collapse baseline rows as a side effect of constructing a temporary serving overlay.
- Candidate-board progress has three separate dimensions:
  - `row_hydration_target_count`: compatibility view of exact visible membership `N` for `/dashboard` + `/candidates` hydration. It is usable only with the same exact membership scope/revision and may include row shells whose card detail is pending.
  - `published_candidate_count`: legacy durable row-publication count retained for diagnostics/history. It must not drive frontend hydration, freshness, totals, or business sync when `row_hydration_target_count` is present.
  - `display_ready_candidate_count`: compatibility view of exact card-ready `C` from the card materialization owner. It never drives row sync, membership, pagination, export/CRM source totals, render gating, or empty-state decisions.
  - `preview_candidate_count`: discovered/published shell rows that are useful as discovery/audit evidence but must not be labeled as materialized cards.
- Canonical `ServingProjection` is the public projection surface, but its dimensions retain separate owners: visible members own `N`; exact card facts own `C`; exact profile facts own `P`; explicit capture evidence owns its own count. Legacy overlays, result-view summaries, and patch metadata are diagnostics and cannot set or max-merge these fields.
- Once a canonical projection link exists, missing/non-exact `board_runtime_state` fails closed. Legacy `result_view_lifecycle.served_candidate_count / expected_candidate_count` is not a public total fallback. Frontend page hydration is shown separately as loaded/cached rows, never as the business sync numerator.
- `delta_profile_board_visible_count` proves row publication into a readable serving projection. It is not, by itself, the user-consumable card denominator. User-facing card progress must come from `board_runtime_state.display_ready_candidate_count` and `card_materialization_status_text`.
- Smoke/runtime reports should expose `service_metrics.board_visible_projection` for baseline+delta workflows. Required signals: `projection_present`, `patch_log_count`, `patch_log_lag_count`, `fetched_to_board_visible_lag_count`, `projection_missing_for_visible_count`, `patch_log_missing_for_visible_count`, and `patch_log_required_missing`. `metadata_replay_dependency` must remain false in normal paths because metadata mirrors are diagnostics, not replay sources.
- Smoke/runtime reports should also expose `service_metrics.snapshot_full_materialization_queue` for terminal or board-visible jobs whose full compaction is still catching up. Required rollups: `backlog_count`, `retryable_count`, `stale_running_count`, `retry_backlog_case_count`, and `stale_running_case_count`. A plain queued background item is not a handoff blocker by itself; retryable or stale-running state remains a service recovery violation because it means the background compaction owner is stuck.
- Smoke/runtime reports should expose `service_metrics.local_apply_backlog` for provider-completion handoff analysis. Required rollups: `applied_not_ingested_count`, `stale_applied_not_ingested_count`, max `age_ms`, `stale_case_count`, `closure_backlog_count`, `closure_retryable_count`, `closure_ready_retry_count`, and `closure_stale_running_count`.
- Profile progress is split into two user-facing lines: `profile_fetch_status_text` reports provider fetch completion over its owned required set, e.g. `新增 LinkedIn Profile 已取回 fetched/required`; `card_materialization_status_text` reports exact card detail `卡片详情已合入看板 C/N`. Do not concatenate them or force their numerators/denominators to match.
- `card_materialization_status_text` must equal the canonical exact `card_ready_count` and exact visible membership for the same revision. It must not be derived from profile-fetched, profile-ready, published-row, capture, or legacy summary counts. The fast smoke preflight `board_runtime_card_text_exceeds_card_readiness` remains a same-field parity check, not a profile/card ordering check.
- When a current snapshot is serving, canonical visible membership owns `expected_candidate_count == served_candidate_count == N`. URL-level delta fetch metrics retain their own required set; lifecycle writers must not normalize profile/card/capture counts to that URL denominator or infer them from full membership. A newly authoritative exact publication may also reduce or clear `N`.
- Terminal lifecycle promotion mirrors the same exact membership revision. It must not compute `N` as `baseline_candidate_count + delta_profile_required_count`, carry a larger legacy expected count, or treat profile terminality as card/membership proof.
- Pressure smoke cases that require final board handoff should set `require_terminal_board_runtime_complete=true`. Cross-endpoint parity alone is insufficient because `/progress`, `/dashboard`, `/candidates`, and `/board-patches` can all consistently expose the same stale `partial_serving` projection.
- The board header may mention filter hit counts and local cached rows, but it must not label `dashboard.candidates.length` as final candidate sync. Once exact membership is published, `sync_status_text` is `N/N` even while cards/profiles trail. Before exact membership exists, sync is pending/unavailable rather than a partial or fallback-backed `X/Y`.
- Candidate-board global filters are a backend index contract. Public facet summaries/counts are published only by the revision-fenced `projection_person_search_index`; frontend hydration windows and direct membership scans are never the source of global facets.
- Initial membership publication sets public facet scope/readiness to `pending` / `unavailable`. `facet_summary_scope="global_full_population"` or `exact_projection` becomes valid only when the index-owned facet product covers the same canonical membership revision. Partial/mismatched products remain unavailable for global counts.
- Public readers trust exact `serving_projection_members` over normalized artifacts, overlays, lifecycle, or summaries. `/dashboard`, `/progress`, and `/candidates` expose `asset_population.candidate_count`, `total_candidates`, and unfiltered pagination total from exact visible membership `N`; filtered totals require the revision-matched search index. A differing legacy value is diagnostic and cannot replace `N`.
- If any stored `public_facet_counts.candidate_count` disagrees with the canonical membership revision/count, public reads fail closed for global facets (`facet_summary_scope="unavailable"`) and do not rebuild facets by scanning members or artifacts. Only a new revision-matched `projection_person_search_index` finalization may publish the next usable facet summary.
- Public lifecycle metadata is a bounded status payload. Patch replay fields such as `candidate_ids`, `cumulative_candidate_ids`, and marker candidate id lists must be exposed as counts in public responses; full replay payloads remain in durable stores/logs, not in `/dashboard`, `/progress`, or `/candidates` polling payloads.
- Public `job.summary` is also a bounded status payload. It may expose allowlisted counters/status fields such as `deferred_url_count`, `profile_fetch_required_count`, and lifecycle/board publication states, but it must not ship local-apply, board-visible, or profile-materialization replay records such as `profile_delta_candidate_records` or `profile_materialized_candidate_records`.
- Candidate-board row filtering is also a backend index contract. `/candidates` applies active filters against the complete exact visible membership through the revision-matched `projection_person_search_index`, then paginates and returns `filtered_candidate_count`. Frontend-loaded windows and card-ready subsets cannot decide filter hits, membership, or whether an empty state is final.
- Dashboard summary reads must be O(stored canonical projection metadata), not O(served board rows). `/dashboard?include_candidates=0`, `/progress`, and `/results?include_candidates=0` consume the exact membership/readiness product and revision-matched index facet product. Legacy `job_result_views`, lifecycle, patch, and overlay summaries remain bounded diagnostics; they cannot fill a missing canonical total or readiness field.
- Large job-scoped overlays are migration/repair artifacts, not a normal public-read source. Caching them may optimize explicit offline repair, but a non-exact canonical projection still fails closed; the cache cannot change membership/readiness counts, facet scope, revision, or fallback reporting.
- `row_publication_watermark` changes must invalidate the current backend-filtered candidate page. The frontend may keep loaded rows as a cache, but the current page membership for active filters must be refreshed from `/candidates`, not from the previously hydrated offset window.
- Execution-page totals use exact `board_runtime_state.expected_candidate_count=N` from the canonical membership revision, not row-publication watermarks or a predicted baseline-plus-delta formula. While no exact revision exists, the total is pending/unavailable; `published_candidate_count` and local hydration are diagnostics only.
- Polling may continue after exact membership reaches `results` to refresh independently pending profile, card, capture, index, or layering products. That tail must not reopen or hide the main `N/N` board; each product terminates against its own owner/scope.
- `expected_candidate_count` is published with the exact membership token and may change only when the authoritative resolver pins another exact token, including downward or to zero. `card_materialization_status_text` always uses that token's `C/N`; `profile_fetch_status_text` keeps its own fetch-required denominator. The legacy `delta_profile_denominator_promoted` flag and baseline-plus-required arithmetic are diagnostic migration evidence, not public count owners.
- Pure shell roster members are valid canonical visible members. Once an exact membership revision publishes them, they count in main sync and pagination even when `display_ready_candidate_count=0`; the card line remains `0/N` and row UI explicitly shows detail pending. Patch-quality fields decide card status, not membership eligibility.
- `local_apply_closure` items in `waiting_prerequisite` are not failures. The path that writes `candidate_documents.json` (search-seed snapshot projection/apply, roster apply, harvest prefetch) MUST kick waiting items immediately via `_reawaken_waiting_prerequisite_local_apply_closure_items` or the store-level equivalent. This includes the case where `candidate_documents.json` exists but does not yet contain rows for the fetched profile batch; a profile batch with fetched URLs, zero resolved candidates, and unmatched profile URLs must wait rather than write a final ingest marker. The bounded `not_before_at` retry (default 8 s, env override `SOURCING_LOCAL_APPLY_WAITING_PREREQUISITE_DELAY_SECONDS`, hard-capped at 30 s) is a fallback safety net for crash/restart/race windows only. `service_metrics.local_apply_backlog.waiting_prerequisite_age_max_ms <= 30000` is the SLO. Any future helper that writes `candidate_documents.json` outside the existing `_apply_background_*_workers_to_snapshot` wrappers MUST also fire the reawaken event, otherwise items strand on the bounded timer.

## Scripted Observation Guardrails

Browser/scripted tests should fail on these product-visible regressions:

- Stage label says `Public Web Stage 2` while profile fetch/materialization is still active and `public_web_stage_applicable=false`.
- Candidate sync is missing, non-exact, or fallback-backed after an exact canonical membership revision exists, or does not show that revision's `N/N`.
- Card/profile/capture text or counters are derived from one another, violate their own `0..N` bound, or disagree with their owner for the same revision. Either `card_ready > profile_ready` or `profile_ready > card_ready` is valid by itself.
- `profile_fetch_required_count > max(deduped_candidate_count, deduped_profile_url_count)`.
- `deduped_candidate_count` or `deduped_profile_url_count` exceeds the sum of the visible Stage 1 lane-returned counts.
- Counts change under the same membership token without an owned publication, unequal tokens are merged/ordered instead of fail-closed and re-pinned, or a newly authoritative exact snapshot is rejected merely because its count decreases or becomes zero.
- Candidate source/result view/snapshot ids diverge.

Realistic fixture quality matters. OpenAI/Lovable scripted cases should keep enough realistic profile fields, locations, employment history, education, worker delay variance, out-of-order completion, and slow-tail workers to exercise filters, materialization cost, and frontend interaction timing. If fixture payloads are synthetic placeholders, the report must call that out as a fixture limitation.

Provider timing metrics must compare provider lifecycle timestamps, not local observer spans. `service_metrics.worker_timeline.out_of_order_completion` should use remote provider start/remote-wait start (`provider_started_at`) with remote completion or scripted ready time. Trace spans are local processing observations and can start late when a webhook is recovered after the actor has already finished.
