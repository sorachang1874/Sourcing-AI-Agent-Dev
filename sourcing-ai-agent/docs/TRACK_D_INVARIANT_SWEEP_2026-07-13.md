## 1-single-writer（6 项）

- **[obligation]** identity_search_budget_grant record（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：Grant owner is declared as plan review owner (§2.1: 'grant 进 §4b owner 矩阵（owner = plan review owner，消费方 = Tier-2 命令）') and revoke is explicitly routed single-writer (event→reducer→plan-review-owner grant command), but the consumption write path is never assigned: §2.1 binds '命令/attempt/扣减/transport' to the issuance identity and the plan doc TD-5 requires 'attempt 创建同事务原子扣减' — i.e. the Tier-2 command's (verification-owner-side) attempt-creation transaction synchronously decrements grant balance and presumably flips active→exhausted. That is a second direct writer on the grant aggregate outside both the owner command and the event→reducer path, with no declared consumption-CAS carve-out. Which module writes the decrement and the active→exhausted transition must be stated (either an explicit sanctioned consumer-side CAS channel on designated balance columns, or routing exhaustion through the grant owner).
- **[obligation]** logical result slot (+consumption CAS)（D0_MODEL_TOOL_RUNTIME_DESIGN）：§2.5 says 'cancel/supersession 原子关槽（open→closed，accepted→superseded）' but never names the writer of these slot-state transitions. The slot is owner-maintained ('owner 为每个 (turn_id, step_id) 维护…逻辑结果槽'), yet cancel originates in the generic control plane; D3 §4c establishes the pattern that generic control (cancel/retry/resume) only touches runtime state and domain-side supersession goes owner control event→reducer→domain command, but D0 does not adopt or reference that pattern for slot closing. If the cancel handler writes slot_state directly, the slot has two writers (turn owner + control plane).
- **[obligation]** ModelInvocationEnvelope（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§6 (and D0 §2.2 invocation_envelope_ref) mandates '单一物理 schema…D0 与 D3 同一物理定义一处落库', i.e. one shared physical store written by at least two different command families (agent.turn/model-turn owner and company_identity_verification owner). No owner module/repository is declared for the envelope store, and no per-row ownership + write-once/immutability rule ('不可变结果侧契约' names immutability of the contract but not who is the sole writer of each row and who may never update it). A shared-table, multi-command-family write surface needs an explicit ownership statement to satisfy exactly-one-owner.
- **[obligation]** migration bridge (file registry + snapshots)（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§4a step 3 makes the resolver read path a writer: '读先 PG 后 bridge（命中记指标）' — every bridge hit on a read/resolve path writes the hit-metric table, and that metric is load-bearing gate state (owner matrix row '迁移桥命中 | bridge | 指标表', consumed by deletion preflight '零命中窗口断言'). Under 'readers never write (including hidden repair-on-read)' this is an undeclared reader-side write; it needs either an explicit telemetry exemption in the owner matrix (with the metric store declared non-domain and its writer named) or routing hits through an out-of-band channel rather than the resolver's own transaction.
- **[wording]** company_identity_verifications current-state table (state transition table)（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§4b transition table contradicts the §5 v6 single-writer split in labeling: row '任意非 human_confirmed → human_confirmed | 人工确认 UoW' reads as the human-confirmation (review owner) UoW writing verification_state, while §5 states human_confirmed is written only by the verification owner's supersession command planned via event→reducer ('review owner 在自己 UoW 记录人工决定…→ reducer 计划验证 owner 的 supersession 命令（写 human_confirmed…）'). Also row 'shadow_would_verify → needs_human / superseded | 过期/policy 升版/新 intent' lists conditions, not the typed owner command (e.g. the expire command named in the verified_accepted row), despite the table header claiming '触发（全部为类型化 owner 事件/命令）'.
- **[wording]** verification_intent (+control epoch, claim generation)（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§4c is ambiguous about which module's transaction mints the intent row: 'intent 在 claim 完成且 ActivityAttempt 创建之后绑定' (owner command writes after claim) vs the v6 R5#2 sentence '后继 intent 只在新 claim + 新 ActivityAttempt 创建事务内铸造' (written inside the claim/attempt-creation transaction, which is generic durable-runtime machinery). If the latter is literal, the generic runtime writes a domain aggregate (intent) owned by the verification owner. One sentence naming the writer (owner command execution UoW that also creates the attempt) would resolve it.

## 2-tenancy（9 项）

A bare intent_id idempotency key is only tenant-safe if intent_id is minted globally unique, which is nowhere stated — the idempotency scope for record and apply must be declared as (workspace_id, intent_id) or intent_id declared globally unique.
- **[obligation]** expiry timer / expire command（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§2.2/§4b: the persisted expiry not-before timer event is specified as "携带 generation" and the expire trigger "CAS 于当前 generation" only — neither the timer-event row identity nor the expire command's CAS predicate names workspace_id (or the (workspace_id, company_fingerprint) target row key). - **[obligation]** Tier-1/Tier-2 project ids as idempotency scopes (query_key / candidate_key / fetch_key)（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§8 defines query_key=q_<hash>, candidate_key=slug hash, fetch_key=normalized-URL hash with no workspace dimension. - **[wording]** judge_call_key (cross-doc alignment)（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：Plan §6 obligation 5 requires judge_call_key to gain workspace/intent-generation/route/schema/policy-revision dimensions, but D3 §8 still prints judge_call_key = (candidate_key, evidence_set_hash, prompt_version) with no note referencing that obligation — the detail doc's text contradicts the plan's already-adjudicated extension.
- **[obligation]** identity_search_budget_grant pre-transport authorization CAS（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§2.1 enumerates the pre-transport CAS predicate as "session+intent+grant 三活跃 + OperationRun/WorkflowCommand 非终态 + claim generation/control epoch + attempt + 精确 grant 签发" — workspace_id equality is not an enumerated term (it is only implicit via the workspace-keyed grant/intent rows). Cursor authorization is deferred to obligation #2 for agent_events only.
- **[wording]** agent tool registry route (GET /api/agent/tool-registry)（D0_MODEL_TOOL_RUNTIME_DESIGN）：§3.3 specifies the new read-only route with serialization and guard details but no authorization statement at all; the tenancy/auth dependency exists only in the plan's §3 table (D1 hosted activation depends on C2 token auth). The D0/D1 batch doc itself should state the route's authorization posture (operator-only or workspace-scoped) pre-C2.

## 3-generation-fencing（12 项）

- **[blocker]** plan_review.identity_result.apply gate watermark（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§2.2 specifies the clearing-direction apply CAS as {workspace + session 当前 revision + verification generation > gate watermark + source 事件 id 匹配} and states the watermark is advanced only on a successful clearing apply, while blocking applies '无视 watermark 直接生效' with NO stated watermark advancement or fence write. This leaves an ABA window in the record→apply race: record(applied, gen N) → reducer plans clearing apply → before it executes, expire/supersession fires a blocking apply (reopens gate, watermark unchanged) → the delayed clearing apply for gen N still passes 'gen N > old watermark' and clears the gate that a logically later blocking event just reopened — contradicting the stated invariant '阻塞方向恒占优——清除方向只能单调向前'. Also '匹配' for source 事件 id is not defined against any stored expectation, so it cannot order the two applies. The commit-owner canonical recheck is only a downstream backstop; the gate-level invariant as specified is unsound. Fix requires blocking applies to also advance/record the watermark (or clearing CAS to re-verify the canonical verification row state, not just generation > watermark).
- **[blocker]** logical result slot (+consumption CAS)（D0_MODEL_TOOL_RUNTIME_DESIGN）：§2.5 accept CAS full condition = '槽 open + 所属 OperationRun/turn/WorkflowCommand 均非终态 + claim/attempt 身份匹配 + schema/route/policy pins 匹配', and consumption/approve/dispatch recheck '槽 generation + …claim/route/schema/policy pins'. None of these include the durable control epoch that D3 §4c v6 (R5#2) introduced precisely to close the requeue→re-claim ABA window: after a generic requeue and before the next claim, the command is non-terminal and its stored claim generation is still the old one, so a late terminal result from the pre-requeue attempt matches every listed condition and wins the slot; the post-requeue attempt's differing result is then quarantined. The identical defect was treated as blocking for the D3 intent and fixed via epoch-increment-at-requeue, but the D0 slot CAS — covered by the same claimed '共享模型调用契约' — was not updated to fence on the control epoch.
- **[obligation]** verification_intent (+control epoch, claim generation) — physical epoch column（AGENT_RUNTIME_PLAN）：D3 §4c requires a 'durable control epoch（与 claim generation 分立、requeue 即变）' on the command, i.e. a second never-reset fencing column beyond claim generation. The plan's migration obligation (§6 item 6) declares only 'workflow_commands 新增永不重置的 claim generation/token 列' — the separate requeue-incremented control-epoch column is neither in pinned schema (pinned workflow_commands has only a resettable attempt counter, per D3 §4c) nor named as an explicit migration obligation.
- **[obligation]** plan_review.identity_result.apply gate watermark — physical columns（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：The apply CAS fences on 'session 当前 revision' and a gate-carried 'identity watermark', but the pinned plan_review_sessions schema is a two-state pending/ready table (plan §0, storage.py:3187/:3196) with no revision or watermark columns, and §4b's migration-0002+ DDL declaration covers only company_identity_verifications/intent/grant on the verification side. The gate-side fence columns (session revision, identity watermark, last-applied source event id) are neither shown to exist nor declared as an explicit migration obligation anywhere (plan §6 does not list them).
- **[obligation]** expiry timer/expire command — generation semantics（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§2.2/§4b specify the expiry timer 'carries generation, CAS at current generation' but never state whether the expire transition (verified_accepted→needs_human) itself advances decision_generation. Every control transition must advance/supersede the fence: if expire flips state at the SAME generation, the watermark comparison ('generation > watermark') and any reader that pinned expected decision_generation cannot distinguish pre-expire from post-expire state — direct ABA material feeding the gate-watermark hole.
- **[obligation]** expiry timer — durable timer persistence（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§4b requires '接受时同 UoW 持久化 expiry not-before 定时事件' scanned by a domain owner, and the timer event must carry the generation used in its firing CAS. The physical store for this generation-carrying durable timer (table/columns) is neither in pinned schema nor declared as a migration obligation in §4b's migration-0002+ list or the plan §6 obligations.
- **[obligation]** Tier-1 commands (verify.evidence: documents.fetch + model judge) — pre-transport fence（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§2.1's pre-transport authorization CAS (session+intent+grant active + OperationRun/WorkflowCommand non-terminal + claim generation/control epoch + attempt + precise grant issuance) is specified only for the Tier-2 grant path. Tier-1 also makes paid provider calls (per-candidate documents.fetch, model adjudication) yet no pre-transport fence against cancel/requeue is stated for it — §8's 'cancel 前置停止；晚到结果按 §4c 隔离' fences only the result side, leaving the cancel→async-convergence window open for Tier-1 wire writes.
- **[obligation]** ModelTurnExecutionContext / D0 live gate — pre-transport fence asymmetry（D0_MODEL_TOOL_RUNTIME_DESIGN）：§2.7's per-call pre-requests.post gate only re-asserts assert_live_provider_access_allowed (environment isolation); it does not re-check claim generation / control epoch / command non-terminal before the wire write. D3 §2.1 (R5#4) added exactly this pre-transport CAS on its side and both docs claim a '共享模型调用契约', but the shared contract as written covers only the effective-route snapshot — the pre-transport execution-identity fence is absent from the D0 half.
- **[obligation]** identity_search_budget_grant — supersede-with-transfer vs in-flight exposure rows（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§2.1's supersede-with-transfer moves '恰好剩余额度' to the new grant atomically, but does not state how remaining balance is computed against cost-ledger exposure rows bound to the old issuance that are still in dispatching/sent/uncertain (worst-case-reserved) states, nor whether the transfer CAS fences on all old-issuance exposure rows being terminal. A physical call in flight at transfer time can be double-counted (worst-case held on old grant + full remainder transferred) or the transfer can under-fence and allow overspend across issuances.
- **[obligation]** agent_sessions/agent_turns/agent_events (D2) — per-session single-writer lease（AGENT_RUNTIME_PLAN）：§2 D2 declares 'per-session 单写者 lease' and per-stream sequence_number/idempotency_key, but no lease fencing token/generation is specified: an expired-lease writer can still interleave writes to agent_turns/agent_events unless writes CAS against a lease generation. The §6 obligation item 2 (agent_events precise projection contract) covers stream identity/ordinals/rebuild but does not name lease fencing, so it is neither designed nor declared as an obligation.
- **[obligation]** migration bridge (file registry + snapshots) — mapped bridge-hit consumption semantics（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§4a defines diagnostic-only needs_human semantics only for 'PG miss 且 bridge 命中而无显式 workspace 映射'. The consumption semantics for a bridge hit WITH an explicit workspace mapping (possible post-backfill, since not-yet-migrated legacy writers keep writing the file registry during the bridge window) are unstated; bridge records carry no version/generation/fence, so any authorizing consumption of a mapped hit would bypass the generation-fenced PG canonical path entirely.
- **[obligation]** cost ledger (reservation + exposure rows) — reservation release CAS conditions（D0_MODEL_TOOL_RUNTIME_DESIGN）：§2.3 says 'confirmed/uncertain 对账后经 CAS 释放未用预留' but does not specify the CAS fence fields: release must be conditioned on all child exposure rows for the reservation being in terminal states (confirmed|uncertain-reconciled|no_call) plus attempt/operation identity, otherwise a release can race a concurrent exposure row sitting in dispatching/sent and free budget for a call that may already be on the wire.

## 4-lifecycle（11 项）

- **[blocker]** identity_search_budget_grant record（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§2.1 declares the grant state enum as `active/revoked/exhausted/reconciled`, but the v6 supersede-with-transfer rule in the same section transitions the old grant to `superseded` ("旧 grant→superseded") — a state not in the declared enum. The grant lifecycle definition contradicts its own transfer rule.
- **[obligation]** identity_search_budget_grant record（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：No full transition table for grant states: the trigger and owner for `active→exhausted` (atomic deduction to zero?) and especially `→reconciled` are never stated (reconciliation is specified for the cost ledger in §8, not for grants), and no time-based expiry/abandonment path exists for a grant whose review session is never finalized. Only revoke and supersede-with-transfer are specified.
- **[obligation]** company_identity_verifications current-state table（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：The §4b table is claimed 全量 with registration-time validation, but has no `pending→verified_accepted` row. In Phase 2 steady state (§2.3 step 4: "Phase 2 … 才产 verified_accepted") a fresh verification must reach verified_accepted; the only path in the table is `shadow_would_verify→verified_accepted` via explicit promotion command, which per TD-7 describes promotion of pre-existing shadow rows. Either the table is missing a row or the doc must state that Phase-2 record still writes shadow_would_verify followed by an automatic per-row promotion command.
- **[obligation]** verification_intent (+control epoch, claim generation)（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：When the record CAS fails for reasons other than supersession (e.g. `review_session 当前仍 pending-review` no longer holds, or a pin mismatch), §4c produces a `not_applied` evidence event but leaves the intent in `pending` with no listed transition to a terminal state and no owner responsible for converging stranded pending intents. intent_state ∈ {pending, applied, cancelled, timed_out, superseded} has no defined path out of pending for the not_applied outcome.
- **[obligation]** plan_review.identity_result.apply gate watermark（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§2.2 says blocking applies "无视 watermark 直接生效" but never states whether a blocking apply advances the identity watermark (or records the blocking generation). If it does not, a delayed clearing apply whose verification generation exceeds the stale watermark but predates the blocking event (expiry/supersession) can re-clear the freshly reopened block. Commit-owner canonical recheck mitigates at commit time, but the gate-level lifecycle is underspecified.
- **[obligation]** expiry timer / expire command + policy invalidation（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：Timer ownership is defined only for the acceptance path (§4b: "接受时同 UoW 持久化 expiry not-before 定时事件"). The `shadow_would_verify → needs_human/superseded` row lists 过期/policy 升版 as triggers, but no timer is persisted for shadow rows and no owner fires their expiry — reader-driven convergence by omission. Additionally, policy invalidation is a listed trigger only for shadow rows: no transition invalidates existing `verified_accepted` rows on an `accepted_policy_version` bump, and the commit-owner recheck (§2.2) verifies generation + valid_until + watermark but not policy-revision currency.
- **[obligation]** Tier-1/Tier-2 commands + envelope（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：The full lifecycle treatment (immutable issuance identity, state enum, revoke path, supersede-with-transfer balance rule) is given only to the Tier-2 grant. The Tier-1 小信封 (§2.1 "not_required + Tier-1 小信封") has no stated issuance identity, exhaustion state, or balance behavior across intent supersession/retry — only TD-5's generic "跨 retry/resume 不重置" at plan level.
- **[obligation]** cost ledger (reservation + exposure rows)（D0_MODEL_TOOL_RUNTIME_DESIGN）：§2.3 (and D3 §8) state that crash rows stuck in dispatching/sent "一律按 uncertain 以 worst-case 预留计,直至 provider 对账或保守消耗", but no owner or timer drives the dispatching/sent→uncertain reclassification, the reconciliation sweep, or the 保守消耗 decision — as written it is an accounting interpretation applied by readers, the reader-driven convergence pattern this class forbids. Also unspecified: release of the parent worst-case reservation when an operation terminates (cancel/fail) with zero or partial physical calls.
- **[obligation]** route registry + effective snapshot（D0_MODEL_TOOL_RUNTIME_DESIGN）：§4 defines rollout_state ∈ {draft, canary, active, retired} but no transition owners/effects, and no policy-invalidation reverse path: the effective_route_snapshot is deliberately frozen at action/approval/command creation and "随 retry 全链传播", so commands queued before a route is moved to `retired` (e.g. incident kill) will keep dispatching against the retired route's pinned config. Nothing (including the per-call live gate) is specified to consult rollout_state and fence in-flight snapshots.
- **[obligation]** scripted replay transcript governance（D0_MODEL_TOOL_RUNTIME_DESIGN）：§2.8 gives each transcript a "保留 TTL" but names no owner or process that enforces expiry/deletion of `runtime/model_turn_transcripts/` — TTL convergence is currently ownerless.
- **[wording]** company_identity_verifications current-state table（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：Wording tension: the transition table contains a `superseded → pending` row (新 verification intent) while the v5 history/current-state prose asserts "不存在 superseded 行原地复活" and that superseded current-state rows are replaced whole-row by the new generation. The table row should be labeled as realized-by-row-replacement (new generation row) rather than an in-place state transition, or the never-resurrect claim reads as contradicted.

## 5-late-partial（4 项）

- **[blocker]** ModelInvocationEnvelope + evidence bundle/adjudication acceptance（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：Truncated/filtered model outputs are not structurally non-authorizing on the D3 judge path. D0 §2.5 establishes the authorizable terminal set {end_turn, tool_calls} and quarantines length/content_filter, and ToolTurnResult carries terminal_reason — but the shared ModelInvocationEnvelope field list (D3 §6 and D0 §2.2 invocation_envelope_ref contents) omits any terminal/finish-reason field, and D3's acceptance predicate #7 ('same_company + high + fallback=none + 身份匹配 + bundle hash 匹配') never requires an authorizable terminal reason. D3 explicitly does not depend on D0 tool-calling, so its judge runs on the legacy prompt-JSON path with no finish_reason surface: a content_filter- or length-truncated response that still parses to schema-valid adjudication JSON (e.g. prematurely closed conflicts[]) can satisfy the model half and the envelope half and authorize shadow_would_verify/verified_accepted. This also contradicts the v6 claim that the envelope is 'D0 与 D3 同一物理定义' while D0's own result contract carries terminal_reason and the shared envelope does not.
- **[obligation]** plan_review.identity_result.apply gate watermark（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§2.2 says blocking-direction applies '无视 watermark 直接生效', but does not state which of the remaining CAS conditions (workspace + session 当前 revision + source event id) still bind the blocking direction, and defines no explicit not_applied/quarantine terminal for an apply command that arrives after the review session is terminal (e.g. expiry/supersession domain event landing after plan.commit has already run). Every other late path in the doc has an explicit no-op terminal (record → not_applied); the late blocking apply against a terminal/committed session has neither a defined fence nor a defined quarantine outcome.
- **[obligation]** identity_search_budget_grant record（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§2.1 grant states are 'active/revoked/exhausted/reconciled', but 'reconciled' has no defined trigger or semantics, and the lifecycle does not specify the fate of in-flight Tier-2 consumption at revoke time: the pre-transport authorization CAS fences calls not yet dispatched, and attempt-creation deduction is atomic (TD-5), but for a fail_closed_until_terminal attempt already past transport when the grant is revoked/superseded-with-transfer, the doc does not say whether its late terminal result's exposure rows and deducted balance reconcile against the revoked grant, transfer with the 'exactly remaining' balance, or are quarantined — 'supersede-with-transfer 携带恰好剩余额度' is ambiguous about balance still held by in-flight attempts.
- **[wording]** expiry timer / expire command（D3_COMPANY_IDENTITY_SELF_VERIFICATION_DESIGN）：§2.2 fences stale expiry timer events via generation CAS ('旧定时器不可失效新决定'), but unlike the record path (explicit not_applied no-op evidence event), a fenced-out timer firing has no stated explicit no-op/quarantine outcome or evidence record — the late timer simply silently loses the CAS, breaking audit parity with the doc's own '晚到/失配一律显式终态' rule.

## 6-cost-honesty（4 项）

- **[obligation]** cost ledger (reservation + exposure rows) / ModelTurnExecutionContext（D0_MODEL_TOOL_RUNTIME_DESIGN）：D0 §2.3 requires 'wire 写之前先落 dispatching' but never states a pre-transport authorization CAS coupled with that exposure-row transition for D0 model calls. D3 §2.1 (R5#4) defines a pre-transport authorization CAS (session+intent+grant active, run/command non-terminal, claim generation/control epoch, attempt, exact grant issuance) for Tier-2, but D0's generic model-call path has no analogous statement that the prepared→dispatching write is fenced by (and in the same UoW as) an authorization/reservation-liveness CAS — D0's fences (§2.5 slot CAS) all sit on result acceptance, after transport. A cancelled/superseded turn can therefore still dispatch a paid call whose exposure row is written but whose authorization was already dead, and the rule's 'debit+authorization CAS before transport in same txn' is only satisfied on the D3 side.

## 8-provenance（5 项）
